# QueryFolio query files

[QueryFolio](https://github.com/cyberneura/queryfolio) is a desktop SQL GUI client. Its
query files are plain text files in a fixed two-level layout, so there is no need to drive
the app: read and write them like any other file, or use the app's own CLI.

The reason to reach for this skill is usually the second half of it — **Run and Log** lets
you get the result of a query that only the user can run (production, behind an SSH tunnel,
credentials you do not have) back into a file you can read.

## Ask the app, don't parse the config

The binary has options that print to stdout and exit without launching a window. They parse
the config through the same path the app does — including `config_override_command`, which
fetches the connections from an external command (1Password etc.) — so this is more reliable
than reading `config.yml` yourself, and it works when the config file holds no connections
at all.

```bash
queryfolio --list-servers   # query files directory + one row per connection
queryfolio --help           # usage, including the open / write subcommands
queryfolio --version
```

`--list-servers` prints `Query files directory: <path>` first, then a table:

| Column | Meaning |
|---|---|
| `NAME` | Connection name — this is what `queryfolio write` takes |
| `ENGINE` | The engine string as configured, not canonicalized — an alias prints as written (`valkey` for redis, `es` / `opensearch`, `mariadb`, `postgresql`) |
| `HOST` `PORT` `USER` `DATABASE` | Where it connects (`-` when unset) |
| `SSL` | See below |
| `SSH` | `yes` when the connection goes through an SSH tunnel |
| `FOLDER` | The folder name under the query files directory |

**Passwords, SSH keys and passphrases are never printed.** `USER` is `(hidden)` for
dynamodb, because there that field is an AWS access key ID rather than a database user —
`(hidden)` means "configured but not shown", which is not the same as `-` ("not set").

`SSL` shows the effective mode for mysql / postgres / redis (`disable` / `prefer` /
`require` / `verify-ca` / `verify-full`) rather than yes/no, because the default `prefer`
falls back to plaintext without verifying the certificate. Other engines show the `tls` flag
as `on` / `off` — except a dynamodb connection with no `host` override, where the flag does
not decide anything and the column shows what the AWS SDK will actually use (`on` for the
regional endpoint, or the scheme of `AWS_ENDPOINT_URL` / `AWS_ENDPOINT_URL_DYNAMODB`), so
`tls: false` still reads `on` there. `invalid` means **"this connection cannot connect with
the settings it has"** (unknown engine, a bad `ssl_mode` on mysql / postgres, an
`ssl_root_cert` paired with a mode that never verifies it) — not "there is a stray value in
the config".

On macOS call the binary inside the bundle; `open -a QueryFolio --args --list-servers` gives
you no output back:

```bash
/Applications/QueryFolio.app/Contents/MacOS/queryfolio --list-servers
```

A version old enough not to have these options treats `--list-servers` as an unknown
argument and **launches the GUI instead** (no output). Fall back to reading the config then.

## Layout on disk

```
~/.config/queryfolio/
├── config.yml                    # connections (config.yaml is used when config.yml is absent)
├── sqlfiles/                     # query files
│   └── <folder>/                 # one folder per connection
│       ├── _queryfolio.md        # auto-generated description of the connection
│       ├── monthly-report.sql
│       └── 20260713-2104.sql     # the app's default name for a new file
└── history/                      # query history (700, files 600, on Unix)
    └── <connection name>.jsonl
```

- Query files are exactly `<sqlfiles_dir>/<folder>/<name>.<ext>` — two levels, no
  subdirectories. The app only lists files directly in the folder whose extension matches
  the connection's engine, and ignores dotfiles.
- `sqlfiles_dir` defaults to `~/.config/queryfolio/sqlfiles`; a top-level `sqlfiles_dir:` in
  the config overrides it. Only a leading `~` / `~/` is expanded (not `~user/`, not
  environment variables), and **a relative path is resolved against `~/.config/queryfolio`,
  not the current directory**.
- `_queryfolio.md` is regenerated by the app and describes the connection in Markdown (name,
  engine, host, port, database, user, read-only, group, whether an SSH tunnel is used — no
  secrets). Read it to learn what a folder targets. Edits to it are overwritten.

## Connection → folder name

`queryfolio --list-servers` gives you this in one shot (the `FOLDER` column). If you have to
derive it yourself:

1. `folder_name:` on the server, if set and not blank.
2. Otherwise `<host>_<engine>_<schema>_<user>` joined with `_`. The connection's `name` is
   **not** used, and missing parts become empty strings, so `_` runs together.

Sanitizing only replaces `/` `\` `\0` with `_`, trims the ends, falls back to `_` when the
result is empty, and prefixes `_` when it starts with a dot. Everything else (spaces, `:`, …)
survives.

| Connection | Folder |
|---|---|
| host `db.example.com`, postgres, schema `prod`, user `app` | `db.example.com_postgres_prod_app` |
| sqlite with schema `/Users/me/data.db`, no host/user | `_sqlite__Users_me_data.db_` |
| `folder_name: my-folder` | `my-folder` |

dynamodb is special: its `user` is an AWS access key ID, so instead of the key itself the
folder uses `key-<hash of the key>`, falling back to the `aws_profile` name only when no key
is set (the same precedence the connection uses to authenticate).

## Writing and opening a file

The CLI resolves the directory, the folder and the extension for you, so prefer it over
building the path by hand. `<connection>` is the connection **name** from the config, not a
folder name:

```bash
# content as an argument
queryfolio write reporting monthly.sql "SELECT * FROM orders LIMIT 10;"

# content on stdin
cat query.sql | queryfolio write reporting monthly.sql

# no content: create it if missing, keep it as it is otherwise, then open it
queryfolio write reporting monthly.sql

# open an existing file by path — note the path uses the FOLDER, not the connection name
queryfolio open ~/.config/queryfolio/sqlfiles/db.example.com_postgres_prod_app/monthly.sql
```

- The engine's extension is appended when missing, and the connection folder is created when
  it does not exist yet (with `_queryfolio.md`).
- Content is written **only when actually given**. An empty stdin counts as "no content", so
  a GUI-style launch (whose stdin is `/dev/null`) cannot silently blank an existing file.
  When content *is* given, it replaces the file wholesale.
- Failures (unknown connection, invalid name, stdin over 10 MiB, I/O error) print to stderr
  and **exit non-zero without opening anything** — check the exit status, do not assume the
  file landed.
- **Both subcommands block when the app is not already running**: they launch it and do not
  return. Run them in the background and do not wait. The file is written before the app
  starts, so a timeout does not lose the content. When a window is already open, the command
  hands the file to it and returns. **Neither holds on Windows**, where the release build is a
  GUI-subsystem binary: the shell returns immediately and does not carry the exit code, so
  read the file back to confirm the write instead of trusting the status there.
- `write` is CLI-only; there is no `queryfolio://write/...` URL (a web page can make the
  browser open a `queryfolio://` URL, and dropping arbitrary SQL where someone will later run
  it is a trap). `queryfolio://open//absolute/path.sql` does exist.
- `open` only accepts a file **directly under a connection folder inside the query files
  directory**, with a known query-file extension. Paths outside it, unknown folders and `..`
  traversal are rejected.

## File names and contents

- The extension follows the engine: `.sql` for postgres / mysql / sqlite / duckdb / dynamodb,
  `.redis` for redis / valkey, `.es` for elasticsearch / opensearch. A file whose extension
  does not match the connection's engine simply does not appear in that connection's list.
- Names containing `/` `\` `\0`, starting with `.`, or consisting only of whitespace are
  rejected by the app (an error, not a rewrite). Follow the same rule when creating files
  directly.
- The content is plain SQL (or Redis commands / Kibana-Console-style requests). There is no
  frontmatter, no metadata header, no sidecar file. UTF-8 is required.
- The file list is sorted by name **descending**, with digit runs compared numerically, and
  the extension excluded from the comparison. Modification time is never consulted. The app's
  default name for a new file is `YYYYMMDD-HHMM.sql` (plus a counter on collision), so names
  that start with a date sort chronologically. Give a file a name that says what it is
  (`performance-tuning.sql`) so it does not disappear among the dated ones.

## Run and Log — get results back from the user

**This is how an agent obtains real query results from a database it cannot reach.** It is
the SQL-editor counterpart of the `runandlog` skill, with the same idea: you write the query,
the user runs it, the result is written back into the same file, you read the file again.

Put `📝` in a line comment immediately above a statement. When the user runs that statement,
the result is written back as a block comment right below it.

What you write:

```sql
-- 📝 Orders per day, last 7 days
SELECT date(created_at) AS d, count(*) FROM orders
WHERE created_at >= now() - interval '7 days'
GROUP BY 1 ORDER BY 1;
```

The file after the user runs it in QueryFolio:

```sql
-- 📝 Orders per day, last 7 days
SELECT date(created_at) AS d, count(*) FROM orders
WHERE created_at >= now() - interval '7 days'
GROUP BY 1 ORDER BY 1;

/* 🗒️ Orders per day, last 7 days 2026-08-16 14:03:21
d	count
2026-08-10	128
2026-08-11	141
*/
```

### Writing the marker

- `📝` goes **directly after the dashes** (`-- 📝 label`). A 📝 in the middle of comment text
  is not a marker. Extra dashes (`--- 📝`) are fine.
- The label is optional (`-- 📝` alone works) and is truncated to 200 characters.
- Only line comments **immediately above** the statement are considered; another statement in
  between makes the marker belong to that one. A blank line breaks the chain too, but only
  outside the range the editor executes — inside it blank lines are skipped. Put the marker
  directly above the SQL and it always works. With several markers in one comment block, the
  one closest to the SQL wins.
- One marker per statement. To collect several results in one round trip, mark each statement
  separately (the user runs them one at a time).
- **SQL engines only** (`.sql`). `.redis` and `.es` use different comment syntax and are not
  supported.

### How the write-back behaves

- **Re-running replaces the existing `/* 🗒️ … */` block** — there is never more than one.
  Notes added inside the block are lost on the next run.
- Conversely, **do not delete existing log blocks when you edit a file**. They are recorded
  results; remove them only when you say you are doing so.
- `*/` and `/*` inside the result are mangled into `* /` and `/ *` (an unescaped `*/` would
  close the comment and leave the following data rows to be executed as SQL; PostgreSQL nests
  block comments, so a stray `/*` would swallow the rest of the file). Do not treat the text
  inside a log block as a verbatim value.
- Results larger than **200 rows** trigger a confirmation dialog first: write everything /
  write only the first 200 rows / write nothing. On top of that the body is capped at roughly
  **200,000 characters total and 2,000 characters per cell** (both are checked per cell, so
  the last one can overshoot a little).
- Four different notes can appear at the end of the body, and they mean different things:
  - `(limited to N rows)` — the user chose "write only part of it" in the dialog.
  - `(the query was limited to N rows)` — the result reached the automatic `LIMIT`
    (`default_limit`, 500 by default). It is written whenever the row count hits the limit,
    so a result that happened to be exactly N rows gets it too.
  - `(the result itself was truncated)` — the backend truncated the result.
  - `(this log was truncated — …)` — the log body hit the character cap.

  **A result carrying any of these may not be the complete answer.**
- A statement with no result set (INSERT / UPDATE / DELETE) writes `(N rows affected)` when
  the engine reports a count.
- **On the SQL engines, a SELECT that matched nothing writes a header row and no data rows** —
  column names are filled in even at zero rows, so a nearly empty block is a real, empty result
  rather than a failed write-back.
- `(no rows)` is written when neither column names nor an affected count could be determined.
  DynamoDB lands here for both of the cases above: PartiQL writes get no count back from the
  API, and an empty PartiQL SELECT has no items to take column names from.
- The body is TSV with a header row, but it is not a faithful dump of the values: tabs and
  newlines inside a cell become spaces, and a **string** cell starting with `=` `+` `-` `@`
  gets a leading `'` (spreadsheet formula guard; numbers are left alone). Split on tabs, but
  do not strip a leading `'` unconditionally — a value that really starts with `'` is written
  unchanged. Drop it only when the character after it is `=` `+` `-` or `@`.
- The write-back happens **asynchronously after the run**, and is skipped (with a toast to the
  user, nothing written) when the editor tab changed, the active schema changed, or the text
  of the executed range no longer matches. Editing the file from outside while the user is
  running it is the usual way to lose the result. If the marker itself was deleted during the
  run, that is treated as a cancellation and nothing is written.
- **If the log block directly below the statement is missing its closing `*/`, nothing is
  written** (adding another block in front of a broken comment only makes the nesting worse).
  Do not break the closing delimiter when editing near a log block.
- Results sit in the `.sql` file in plaintext afterwards. Delete the log block once you have
  read what you needed if it contains personal data or credentials.

### The loop, in practice

1. Write the statement with its marker — one command with the CLI. **Passing content replaces
   the whole file**, so use a name you have not used yet, or read the existing file first and
   pass it back with your statement appended; an earlier round's queries and log blocks live
   in there:

   ```bash
   queryfolio write <connection> investigate-orders.sql "$(cat <<'SQL'
   -- 📝 Orders per day, last 7 days
   SELECT ...;
   SQL
   )"
   ```

2. `queryfolio open <path>` hands the file to the running window. If you placed the file
   without using the CLI at all, say so — the app does not scan the directory, so the file
   does not appear in the FILES list until the user switches connections. (Both commands
   launch the app and block when no window is open; run them in the background.)
3. Tell the user to put the cursor on the statement and run it.
4. Read the file again and parse the `/* 🗒️ …` block.

When the user is busy, mark several statements at once and get all the results in one round
trip.

## Query history

`~/.config/queryfolio/history/<connection name>.jsonl` — note this is the connection's
**name**, not the sqlfiles folder name. One JSON object per line, appended oldest-first:
`time` (RFC 3339), `sql`, `schema`, `row_count`, `elapsed_ms`, `success`. Above 10,000 lines
it is rotated down to the newest 9,000.

Useful for "that query I ran the other day":

```bash
find ~/.config/queryfolio/history -name '*.jsonl' -exec cat {} + 2>/dev/null \
  | jq -r 'select(.success and (.sql | test("orders"))) | "\(.time)\t\(.sql)"'
```

> Do not glob `~/.config/queryfolio/history/*.jsonl`. With no history yet, zsh refuses to run
> the command at all (`no matches found`, which `2>/dev/null` does not suppress) and bash
> passes the unexpanded string to `cat`. The `find` form above returns empty quietly in both.

SQL text can contain secrets, which is why the directory is 700 and the files 600. Do not
ship the contents somewhere else casually.

## Pitfalls

- **The app does not watch the directory.** A file created or deleted from outside does not
  show up in the FILES list until the user switches connections or reloads the config. Say so
  when you create one without the CLI — opening a file through the CLI (`open` or `write`)
  refreshes the list on the way in.
- **Files open in a tab are watched, though** (polled every 2.5 s). An external edit is
  reloaded automatically when the tab has no unsaved changes, 3-way merged when the edits
  touch different places, and flagged as a conflict otherwise — the user then resolves it with
  Overwrite / Discard in the editor toolbar. Your edits will not be silently overwritten, but
  a conflict does stall the user, so prefer editing files that are not currently open.
- **Permissions are handled by the app; do not loosen them.** On Unix, directories it creates
  under `sqlfiles/` are 700 and files it creates are 600 (matching `history/`), while
  directories that already exist keep whatever mode they have — an install predating this
  behaviour can still have a 755 `sqlfiles/`. `config.yml` is created as 600, rewritten as
  600, and tightened to 600 on load, since it can hold database passwords and SSH passphrases
  in plaintext. On Windows all of this is left to ACL inheritance.
- **The config file is not necessarily `config.yml`.** The app prefers `config.yml` and falls
  back to `config.yaml`, reading only one of them. Resolve it the same way rather than
  assuming, and never grep both at once — a leftover `config.yaml` from a migration would give
  you the wrong `sqlfiles_dir`:

  ```bash
  CONF=~/.config/queryfolio/config.yml
  [ -f "$CONF" ] || CONF=~/.config/queryfolio/config.yaml
  ```

- When `QUERYFOLIO_CONFIG_YAML` holds a non-empty value for the running app (a development /
  E2E hook), the app uses that variable's contents as the entire config and reads no config
  file at all. A blank value is ignored and the config file is read as usual.
- In `config.yml` the connections live under the top-level `servers:` key. The old name
  `sql_servers` is not accepted — the app refuses the config with a message telling you to
  rename it. The window still opens; you get that error and no connections rather than a
  silent empty list. When `config_override_command` is set, the connections may not be in the
  file at all; use `queryfolio --list-servers`.

## Where the behaviour lives

In the QueryFolio repository: `src-tauri/src/query_files.rs` (CRUD, path traversal),
`src-tauri/src/config.rs` (`resolve_sqlfiles_dir` / `sqlfiles_folder_name`),
`src-tauri/src/history.rs`, `src-tauri/src/cli.rs` (`--list-servers` and friends),
`src-tauri/src/router.rs` (`open` / `write` and the `queryfolio://` URI). Run and Log is on
the frontend: `src/lib/runLog.ts` and `writeRunLog` in
`src/lib/components/SqlEditor.svelte`.
