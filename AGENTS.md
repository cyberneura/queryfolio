# queryfolio

A desktop app that aims to be a multi-purpose SQL GUI client.

## Tech stack

- **Tauri 2** (Rust backend + WKWebView)
- **SvelteKit + Svelte 5 (runes)** / TypeScript / Vite 6
- **Tailwind CSS 4** (@tailwindcss/vite plugin style)
- **CodeMirror 6** + @codemirror/lang-sql (SQL editor)
- **Bootstrap Icons** (the bootstrap-icons package; the CSS font is imported in app.css)
- **sqlx 0.8** (MySQL / PostgreSQL / SQLite)
- **tiberius 0.13** (Microsoft SQL Server. A pure Rust implementation of TDS; TLS is vendored OpenSSL)
- **ssh2** (SSH local port-forward tunnels)
- Package manager: pnpm

Tauri 2 / Svelte 5 / Tailwind 4 are relatively new, so when unsure about an API, consult the docs through the context7 MCP.

## Commands

```shell
pnpm tauri dev          # Start in development (Rust build + vite dev + native window)
pnpm check              # svelte-check (type check)
cd src-tauri && cargo test   # Rust unit tests
cd src-tauri && cargo check  # Rust type check
pnpm tauri build        # Release build
pnpm local-deploy       # Build the .app → sign with Developer ID (no notarization, no timestamp) → replace it in /Applications (replaces the version installed by Homebrew; brew upgrade only switches back once a newer version is published)
pnpm release            # Assign the version → push to main (this starts the release) → watch (patch|minor|major)
fab release             # Same as above (fab release:minor etc.)
fab -l                  # List fab tasks (dev / check / unittest / build_local / release / releases)
```

A release starts when the version in `src-tauri/tauri.conf.json` changes on main (`on: push` in `.github/workflows/release.yml`. The `plan` job uses `scripts/release-decide.sh` to ask the releases API "is this version unpublished, and newer than the latest published one?", and proceeds to the build only when it is — because the decision is based on state rather than a diff, squash / rebase / direct push do not change the outcome). The `draft` job prepares one **draft** Release, the macOS universal dmg and the Windows NSIS installer (unsigned) are built in parallel in a matrix and uploaded to that draft → after all platforms succeed, the `publish` job publishes it. Version assignment and the push are done by `scripts/release.sh` (`pnpm release` / `fab release`), which then watches the run started by the push (it does not start one itself). Design details are in the global skill `tauri-github-actions-release`, and the runbook up to publication is the `publish-macos-release` skill (`.claude/skills/publish-macos-release/`; includes the first-time setup of the signing Secrets). Key design points:

- **Separating draft → publish is mandatory**: the two matrix jobs upload to the same `v<version>` Release, so uploading to a published Release would immediately publish an incomplete Release containing only the job that finished first.
- **macOS does not use tauri-action**. The tauri CLI (`pnpm exec tauri build`) applies the Developer ID signature + notarization + staple to the .app, and only signs the dmg. If the dmg is not notarized, a downloaded dmg becomes `rejected / source=Unnotarized Developer ID` under `spctl -a -t open --context context:primary-signature`. tauri-action does build and upload in one step, so dmg notarization cannot be inserted in between. Therefore macOS is split into build → `notarytool submit --wait` (judged by both the exit code and `status: Accepted`; on failure, prints `notarytool log`) → `stapler staple` / `validate` → `spctl --type open` → upload to the draft Release by release ID via `gh api` (uploads.github.com) (an asset with the same name is deleted first, in case of re-runs). Windows stays on tauri-action.
- **The draft is created once, before the builds, by the `draft` job, and is passed to tauri-action (Windows) and the macOS upload by release ID** (no `tagName` is passed). With the tagName approach each job does "look it up in the list and create it if missing" after its build, so if both builds finish at nearly the same time, two drafts with the same tag are created and publish releases one of them missing a platform. A failed run's draft is reused, and its `target_commitish` is fixed to that run's commit (publishing with the commit where the draft was first created would make the tag disagree with the contents). If there are two or more drafts with the same tag, it stops because it cannot decide which one to upload to (delete the unneeded drafts and re-run).
- **Never release a version older than the latest published one** (`release-decide.sh`). This is so that a revert of a version-bump commit, or pending runs being processed in the reverse order of the pushes, does not roll back the latest release and the Homebrew tap via the `--latest` equivalent (`make_latest`).
- **`publish` repeats the same decision right before publishing**. "Re-run failed jobs" does not re-run a successful `plan` and reuses its old decision, so if a newer version was published in the meantime, it would roll back the latest. `scripts/release.sh` likewise does not report Done just because the run succeeded; it confirms the Release is not a draft (because a run whose plan returned release=false also ends in success).
- **The version must be incremented every time**: `plan` rejects already-published versions, so forgetting to bump means nothing is released. That is why `scripts/release.sh` automates the numbering (structurally eliminating forgotten-bump accidents).
- **`pnpm publish` cannot be used** (it is a pnpm built-in command and cannot be overridden). The command name is `release`.
- **Every `uses:` is pinned to a commit SHA** (the trailing comment is the original tag). These jobs handle Apple certificates and credentials, so a tampered action could reach the Secrets or the keychain in later steps. checkout uses `persist-credentials: false` so a token with write permission is not left in `.git/config`. `APPLE_*` is passed only to the macOS steps.
- **The tauri CLI is invoked as `pnpm exec tauri`** (the macOS build step, and `tauriScript` of tauri-action on Windows). If `tauriScript` is omitted, tauri-action runs `pnpm tauri build` for pnpm projects, which runs the `tauri` script in package.json (`APPLE_SIGNING_IDENTITY='...' tauri`). An inline shell assignment beats the inherited env, so **the `secrets.APPLE_SIGNING_IDENTITY` passed by the workflow would be silently ignored** (and on the Windows shell it is a syntax error as well). `pnpm exec tauri` does not go through the script.
- **`cancel-in-progress: false` + `queue: max`**: 1 push = 1 version, so a cancelled run's version stays unpublished (while the bump commit stays on main) (it can be picked up again with `workflow_dispatch`, but if nobody notices, it is the same thing). Protecting the running run (`cancel-in-progress: false`) is not enough: the default `queue: single` holds only one pending run and discards the existing pending one on a new push, so `queue: max` (up to 100) is also needed. Not dropping releases is prioritized over CI minutes.
- **Homebrew distribution**: `brew install --cask cyberneura/tap/queryfolio` (the tap is cyberneura/homebrew-tap, `Casks/queryfolio.rb`). **The cask is updated hourly by the tap side** (the tap's `scripts/update.py` looks at each project's latest release and rewrites version / url / sha256). Do not push to the tap from this repository — doing so would mean handing a PAT that can write to the tap to every project. The former `homebrew` job and the `HOMEBREW_TAP_TOKEN` secret are no longer needed (CYBERNEURA-DEV-481).
- **Weakness**: `pnpm release` pushes directly to main, so it breaks if branch protection (PR required) is enabled (if the version change is merged through a PR instead, the workflow side works unchanged).

## Architecture

### Rust (src-tauri/src/)

| File | Role |
|---------|------|
| lib.rs | Tauri command definitions and AppState (connection config cache + DbManager), building the menu bar (build_menu / rebuild_menu) |
| config.rs | Loading config.yml, recursive merging of the config via config_override_command (load_merged / merge_mapping), template expansion, expand_tilde, reading/writing for the config editor (read_config_file / write_config_file). Running commands written in the config (config_override_command / password_command) is unified in `run_setting_command` (shlex, no shell, PATH supplementation, timeout, kill_on_drop. Errors include the command and stderr but not stdout. Deciding what counts as empty output is up to the caller — password only strips trailing CR/LF, so a whitespace-only password also passes) |
| settings.rs | Reading/writing the general settings of the Settings window (CYBERNEURA-DEV-1298). Pure logic + unit tests that depend neither on Tauri nor on the rest of config.rs (`read_local_settings` / `apply_patch` / `save_patch` / `override_key_paths`). Serialization of writes to config.yml (`CONFIG_WRITE_LOCK`; the text editor and file-connection appends also go through it) and the atomic write that writes to a symlink's target (`write_atomically`) also live here. Details in "Settings window" under the frontend |
| connections.rs | Reading/writing for the connection editor (CYBERNEURA-DEV-1299). Returns the local `servers` with secrets (`password` / `ssh_tunnel.password` / `ssh_tunnel.private_key_passphrase`) removed (`read_local_servers`); saving replaces `servers` wholesale (`apply_connections`). The frontend does not have the secrets, so they are carried over from each entry's `origin` (the index path at read time), and changes are received as set / unset. If the `revision` (hash of servers at read time) differs from the current file, nothing is written. The new list is checked with the same parser as the app (`parse_server_entries`, including template expansion) + duplicate names + the `password_command` rules before writing. Key order is the original entry's order → the default order (because serde_json reorders keys) |
| db.rs | sqlx pool management (running password_command and re-fetching after expiry = `with_pool` / `run_with_password_refresh` / `PasswordRetry`; details under password_command in "Config"), query execution and cancellation (CancelRegistry. The result-table `run_query` also registers in `QueryRuns` at its entry; `cancel_query` aborts only the future if there is no server-side cancel target yet (waiting for the connection / `CONNECTION_ID()`), and when the server-side cancel fails / does not respond within 10 seconds / the query has not finished 5 seconds after a successful cancel, it discards the connection's pool and tunnel and then aborts. The connection is not discarded merely because there is no target — the run may just be waiting behind healthy work on the same connection (a full pool, the SQL Server client's lock), and discarding would take that down with it. An aborted run that discards does not return until the discard finishes (`finish_run`; returning first lets a late disconnect cut the pool of the next query). Registration in the CancelRegistry happens after acquiring the connection, so on its own, when the tunnel goes silent you end up with "frontend running, backend has no cancel target" and neither new queries nor cancel get through. Only the waiting part is aborted; rolling back `\c` / `USE` always runs. Full-row fetches for Copy / Export are excluded (they are not "running" in the UI and can run in parallel with the user's query)), per-type JSON conversion, the readonly guard / dangerous-statement guard (dangerous_reason). Engines that do not use sqlx (Redis / Elasticsearch / DuckDB / DynamoDB / SQL Server) are held as variants of `DbPool` and delegated to the modules in engines/ at the start of run_query_cancellable. `scan_sql` skips square-bracket identifiers (`[name]`, `]]` is the escape) as quotes for MsSql only |
| engines/mod.rs | Core of the pluggable engine layer. `EngineCapabilities` (editor language, query file extension, support for schemas/tables/explain/format/cell editing/AI) is declared per engine and passed to the frontend as `ConnectionInfo.capabilities`. Because the frontend switches UI by capability rather than engine name, adding an engine only takes "add a module to engines/ + declare capabilities + add a variant to the enum in db.rs" |
| engines/redis.rs | Redis engine (engine: redis / valkey). 1 line = 1 command (a tokenizer with redis-cli-compatible quoting and escaping); multiple lines are executed sequentially on the same connection. The readonly guard is a whitelist of read commands; dangerous commands (FLUSHALL / FLUSHDB / SHUTDOWN / DEBUG) are treated like the SQL dangerous-statement guard. RESP values are converted to tables: Map = field/value, even-length flat arrays (RESP2) from pair-returning commands (HGETALL / CONFIG GET) are also field/value, Array = one row per element, scalar = one cell, multiple commands = command/result. Arguments are byte strings for binary safety (\xHH escapes are raw bytes). Cancellation aborts the future on the client side (`CancelTarget::ClientSide`). A multiplexed connection is opened per execution (so abandoning it on cancel does not break a pool). The schema is the database number, SSH tunnels are supported, and pub/sub and blocking commands (BLPOP / XREAD BLOCK etc.; the connection stays blocked even after cancel) are rejected |
| engines/duckdb.rs | DuckDB engine (engine: duckdb). It is an SQL engine, but sqlx has no DuckDB driver, so it is wired with the `duckdb` crate (bundled, C++ sources statically linked). The connection is like sqlite (`schema`, or `host` if absent, is opened as the DB file path. If the file does not exist it is an error, it is not created. No SSH tunnel). duckdb::Connection is Send but not Sync, so one connection is kept as `Arc<Mutex<Connection>>`, and synchronous API calls are wrapped in spawn_blocking. The common SQL guards (meta-command translation → readonly → dangerous → auto LIMIT) reuse the existing logic in db.rs (is_readonly_allowed / dangerous_reason / should_auto_limit / scan_sql; dialect is Postgres-like = dollar quoting supported). Cancellation is a server-side interrupt via duckdb's `InterruptHandle` (`CancelTarget::DuckDb`) (required because spawn_blocking does not stop when the future is dropped. A cancel that arrives before execution starts is caught by a flag check on the blocking side). Type conversion: integers beyond 2^53 / HUGEINT / DECIMAL become strings, TIMESTAMP / DATE / TIME become strings, LIST / STRUCT / MAP become JSON with an element cap (1,000) and set truncated. EXPLAIN uses the prefix `EXPLAIN` (EXPLAIN ANALYZE is not used because it executes the target statement). The schema browser / SQL completion / PK query information_schema and duckdb_constraints(). Cell editing (run_statements) is not supported because it goes through sqlx (capabilities.supports_editable_cells = false) |
| engines/elasticsearch.rs | Elasticsearch engine (engine: elasticsearch / es / opensearch). Calls the REST API directly with reqwest instead of sqlx (`EsClient` = base_url + Basic auth; `tls: true` for https). The editor uses Kibana Console-style request blocks (a method line like `GET /index/_search` + a JSON body. `#` lines are comments; NDJSON bodies are sent as-is for `_bulk`). Running a selection of multiple blocks yields a request / status / result table (HTTP error statuses are included as rows and execution continues; transport errors abort). Result formatting: hits.hits → a table of `_index`/`_id`/`_score` + the union of `_source` keys; arrays of objects (`_cat/...?format=json`) → a table of the key union; anything else → one cell of pretty JSON (100,000-character cap). Every formatting path applies max_rows / per-cell character and element caps + truncated, and the response body is read up to 20MB. The readonly guard always allows GET/HEAD + a whitelist of search APIs for POST (the first `_` segment is taken as the API, preventing an ID bypass like `/index/_doc/_search`). The dangerous guard covers DELETE of a single segment (index deletion) and `_delete_by_query`. Path segments `.`/`..` (including percent-encoded forms) are rejected to prevent URL normalization mismatches between validation and actual I/O. GET / at connect time and every request have timeouts. Cancellation is `CancelTarget::ClientSide`. The TABLES pane shows the index list from `_cat/indices` (excluding system indices starting with `.`) + fields from the `_mapping` properties flattened to `a.b` form |
| engines/dynamodb.rs | DynamoDB engine (engine: dynamodb). Executes PartiQL (an SQL-compatible subset) via the ExecuteStatement API of the AWS SDK (`aws-sdk-dynamodb`). The editor is a regular SQL editor (editor_language "sql" / extension .sql), and the readonly / dangerous guards reuse the SQL logic in db.rs (PartiQL only has SELECT / INSERT / UPDATE / DELETE. Double-quoted identifiers are blanked out by scan_sql as strings, but keywords like WHERE are not quoted, so the decision is unaffected). Connection: `schema` = AWS region (required), `host`/`port` = endpoint override (for dynamodb-local; `tls` selects http/https), auth is user/password (static access key) → `aws_profile` (a queryfolio extension) → the default credentials chain, in that order. The connection check runs ListTables (limit 1) with a 15-second timeout. PartiQL has no LIMIT clause, so auto LIMIT is not applied; instead it uses ExecuteStatement's limit parameter + NextToken pagination, cutting off at max_rows + 1 and reporting truncated (with a 120-second deadline for the whole pagination, because a SELECT with a strong filter can produce a long run of empty scan pages). INSERT / UPDATE / DELETE cannot get the affected row count from the API, so affected_rows = None + an empty result (Items from `RETURNING ALL OLD *` are shown as a table as-is). Result formatting uses the union of Item keys (sorted, because SDK Items are HashMaps with no key order) as columns; AttributeValue → JSON turns N (arbitrary precision) into a number only for safe integers and a string otherwise, B/BS use bytes_to_json, and L/M/SS/NS/BS are cut off with a shared per-cell budget (1,000 elements), a depth cap of 32, and 10,000 characters per string + truncated. Cancellation is `CancelTarget::ClientSide` (a biased select that checks the result side first). The HTTPS client explicitly uses the ring-based rustls, same as the existing dependencies (the SDK default aws-lc needs cmake / NASM for its native build, which is a CI risk). The TABLES pane shows ListTables (up to 5,000) + the DescribeTable key schema (partition / sort key) and attribute definitions (data_type in S/N/B notation). Meta-commands / \c / EXPLAIN / cell editing / AI / SSH tunnels are not supported |
| engines/mssql.rs | Microsoft SQL Server engine (engine: mssql / sqlserver, CYBERNEURA-DEV-965). sqlx has no driver, so it is wired with `tiberius` (a pure Rust TDS implementation). The TLS backend is **vendored OpenSSL** (`vendored-openssl` = opentls; the same static linking of openssl-src as ssh2) — neither the default native-tls (macOS's Security Framework does not work with SQL Server's TLS, as stated in the tiberius README) nor rustls (it pulls tokio-rustls with the default feature (aws_lc_rs), bringing into CI the aws-lc-sys native build that dynamodb avoids) is used. Connection: host / port (default 1433) / `schema` = database (master if omitted) / user + password, SQL Server authentication only (integrated auth, Azure AD, and named instances are not supported). SSH tunnels are supported. `ssl_mode` / `tls` / `ssl_root_cert` map the same keys as mysql / postgres onto tiberius's EncryptionLevel (disable = NotSupported / prefer = **Off** + trust_cert = the login packet is always encrypted and the rest follows what the server offers. `On` causes a protocol error against Off / NotSupported servers and cannot downgrade / require = Required + trust_cert / verify-ca, verify-full = Required + certificate verification. SQL Server has no setting that verifies only the chain, so verify-ca is the same as verify-full. Through a tunnel, hostname verification uses the configured `host` via `hostname_in_certificate`). The connection for user operations is kept as one `Mutex<Option<Client>>` to serialize execution; cancellation aborts the future, then sends `cancel_query` (a TDS Attention, 10-second cap) on the same Client to stop the server side too, and **discards that connection** (`CancelTarget::ClientSide`. It is not reused because the cleanup of SHOWPLAN / transactions opened inside the aborted future has not run). command_timeout is disabled (the default 30 seconds kills heavy aggregations). The common SQL guards (meta-commands → readonly → dangerous) reuse the logic in db.rs, supplementing only what T-SQL lacks. **T-SQL lets you omit `;`**, so on connections where the guard is active, besides the `;` multi-statement check, a statement in which a write / control / execute keyword (`TRAILING_STATEMENT_KEYWORDS`) appears after the first statement is also rejected as multi-statement (because `SELECT 1\nDROP TABLE t` would otherwise pass on the leading SELECT alone. `select` / `with` are not included — subqueries and `WITH (NOLOCK)` appear within a single statement. What gets added to the list is "T-SQL reserved words that can start a statement without `;` and that write data or change server / session state" (reserved words cannot be used as bare column names or aliases, so false positives do not increase. `writetext` / `updatetext` / `reconfigure` / `checkpoint` / `setuser` / `revert` / `waitfor` (`WAITFOR (RECEIVE ...)` removes messages from a queue) were added in CYBERNEURA-DEV-1060. Non-reserved `enable` / `disable` / `send` / `receive` either become an alias after SELECT or require a preceding `;`, so they are stopped by the `;` check. `fetch` is not included because it appears in `OFFSET ... FETCH NEXT`. A word written right after a numeric literal (`SELECT 1DROP TABLE t`) is a separate word in T-SQL's lexer, so literal parts (including `$` money) are stripped before the check. Word boundaries follow the regular identifier rules (Unicode letters/digits and `_` `@` `#` `$`), so `foo$checkpoint` and `@update` are not false positives): **auto LIMIT inserts `TOP (n)`** into the SELECT (after DISTINCT / ALL) (`apply_auto_top`; not applied to statements containing TOP / OFFSET / FETCH / INTO / FOR / set operations / DML / OUTPUT, or to WITH), **EXPLAIN is a pseudo-statement** that sends 3 batches `SET SHOWPLAN_ALL ON` → the target statement → OFF and returns the estimated execution plan rows (nothing is executed. If OFF fails, the connection is discarded), **the agent path opens a dedicated connection, wraps it in `BEGIN TRANSACTION` / `ROLLBACK`, and discards it** (SQL Server has no READ ONLY transactions. Consumption of NEXT VALUE FOR / IDENTITY is not undone. Running it on the user's connection would have the ROLLBACK take down a transaction the user left open — nested transactions are not independent). Only "leading keywords that return no rows and whose affected row count matters" like INSERT / UPDATE / CREATE (`NO_ROWS_KEYWORDS`, no OUTPUT clause, not touching `#temp`) get the affected row count via sp_executesql (execute); everything else is sent as a batch (simple_query) and the first result set becomes the table (affected rows None). **sp_executesql has procedure scope, so `SET` session settings, `BEGIN TRANSACTION`, and `#temp` creation done inside it vanish when the call ends** — these, plus scripts starting with EXEC, `IF EXISTS (...) SELECT`, or DECLARE, go through the batch side. Format is made available by giving the frontend's `sqlFormat.ts` an mssql dialect (keeping square-bracket identifiers and `#temp` as tokens). Value conversion: BIGINT beyond 2^53 and DECIMAL / NUMERIC become strings, date/time goes through chrono in the same format as db.rs (DATETIMEOFFSET is RFC 3339), VARBINARY uses bytes_to_json, strings are cut at 10,000 characters + truncated. The schema browser / SQL completion / PK query INFORMATION_SCHEMA with parameter binding (@P1) (table names do not go through validate_relation_name; `qualified_name` brackets every part without omitting dbo, and `split_qualified` turns the `[dbo].[users]` / `[sales].[orders]` form back — for names containing reserved words, spaces, or dots, and for logins whose default schema is not dbo); the database list is from sys.databases. `\c` / `USE` (square-bracket quoting allowed; `USE [Sales Data]` is read as an identifier before splitting on whitespace) reconnects with a schema override. Cell editing (run_statements) is not supported because it goes through sqlx (capabilities.supports_editable_cells = false) |
| dump.rs | DB / table dumps (CYBERNEURA-DEV-1070). Rather than inventing a format, it **launches mysqldump / pg_dump as child processes** (so the output can be restored with `mysql` / `psql` / `pg_restore`). Only mysql / postgres, where the capability `supports_dump` is true. Key design points: (1) **Binary detection** (`detect_tools`) — a GUI launch does not inherit the shell's PATH, and Homebrew's `mysql-client` / `libpq` are keg-only, so in addition to the supplemented PATH it globs known locations (`extra_dir_patterns`: Postgres.app / bundled with MySQL Workbench / Linux `/usr/lib/postgresql/*/bin` / Windows Program Files) and returns them with the first line of `--version` (5-second cap). **Only pg_dump lists newer versions first** (a pg_dump older than the server refuses to dump). mysqldump keeps the discovery order with PATH first. The frontend remembers the chosen path and extra arguments per tool in localStorage (`queryfolio.dump.toolPath.<tool>` / `queryfolio.dump.extraArgs.<tool>`). (2) **The password is never put on the command line** (other users can see it with `ps`). mysqldump uses a temporary option file (`--defaults-file`, **always the first argument**, created with 600 + `create_new`, deleted when the dump ends. Values use backslash escaping inside double quotes. Even with no password, an empty `[client]` is passed), and pg_dump uses the child process's environment variable `PGPASSWORD`. pg_dump gets `--no-password` (there is no terminal, so it must not hang waiting for a password). **`--defaults-file`, not `--defaults-extra-file`** — an extra file is read before the user's `~/.my.cnf`, so the `password` there would override the configured password, and `[mysqldump] result-file=` / `tab=` would divert output around the temporary file. With `--defaults-file`, no other option files are read. `.mylogin.cnf`, which is still read with `--defaults-file`, is shut out by pointing the environment variable `MYSQL_TEST_LOGIN_FILE` at a nonexistent path. For connections without a `user`, `root` is given explicitly with `--user`, same as sqlx (the mysql client's default is the OS username). (3) **An SSH tunnel is opened just for the dump and closed when it ends** — borrowing the tunnel cached by `DbManager` would let a disconnect / schema switch / config reload during the dump drop it and cut the dump midway. pg_dump separates `hostaddr` = the tunnel / `host` = the configured hostname even through a tunnel, so verify-full passes. The mysql client has no such distinction and connects to 127.0.0.1 like the app's own connection (verify-full through a tunnel fails on the certificate hostname). (4) TLS mirrors the connection's `sql_ssl_mode`: mysqldump gets `--ssl-mode=` (require is `--ssl --skip-ssl-verify-server-cert` for MariaDB, because clients from 11.4 on verify the certificate by default. MariaDB's client has no `--ssl-mode`, so if `--version` shows `MariaDB` (or, if it cannot be run, the file name contains `mariadb`; `is_mariadb_client` is shared between preview and execution) it uses `--ssl` / `--skip-ssl` / `--ssl-verify-server-cert`); for `prefer`, the MySQL client gets nothing and is left to its default (try TLS), while the MariaDB client gets `--ssl --skip-ssl-verify-server-cert`, the same as require (because the default before 11.4 is plaintext and from 11.4 on it verifies the certificate by default). pg_dump uses `PGSSLMODE` / `PGSSLROOTCERT`. mysqldump always gets `--protocol=TCP` (without it, `localhost` becomes a Unix socket, a different route from the app (sqlx) and the tunnel). (5) Name handling: mysqldump's DB and table names are positional arguments, so names starting with `-` are rejected. **pg_dump's connection target — host / hostaddr / port / user / dbname — is passed entirely as one libpq connection string (`--dbname=host='..' dbname='..'`, values in single quotes with `\` and `'` escaped)**. In addition, `PGHOSTADDR` / `PGSERVICE` / `PGSERVICEFILE` are removed from the child process's environment (libpq fills parameters missing from the connection string from environment variables, so an inherited PGHOSTADDR would replace the target. sqlx reads neither) — with `--dbname=<name>`, a DB name containing `=` (which comes from the server's DB list) would itself be interpreted as a connection string, and `host=` could redirect it, PGPASSWORD and all, to another host. pg_dump's `--table` is a psql pattern where `*` `?` `.` and uppercase are interpreted, so **every part is wrapped in double quotes** (`"Sales"."order*s"`, inner `"` doubled). The frontend passes tables as `schema` + `name`, not qualified_name. (6) **Output is written to a unique temporary file in the same directory (`.<name>.<pid>-<nanos>-<n>.partial`, `create_new` + 600) and renamed only on success** (deleted on failure / cancellation. A half-finished dump is never left under the real file name. A fixed name would break existing files and concurrent dumps to the same destination. 600 because a dump is the DB's contents themselves). Extra arguments that change the output destination (pg_dump's `-f` / `--file`, mysqldump's `-r` / `--result-file` / `-T` / `--tab`. Both tools accept abbreviated long options, so prefix matching is used (the mysql client treats `_` and `-` as the same and accepts a `loose-` prefix, so it normalizes first); combined short options (`-vf out.sql`) are also parsed, and what follows an option that takes a value is treated as that value) are rejected — they would bypass the temporary file and an empty file would be saved as the result. A data-only dump includes no definitions (mysqldump gets `--skip-triggers` and no `--routines --events`). For pg_dump's custom format, `--clean` / `--no-owner` are not added (they are ignored for archives and decided on the pg_restore side). The last 64KB of stderr is kept and returned as the error on failure and as warnings on success. (7) Progress sends the written file size every 500ms as a `dump-progress` event; cancellation is `cancel_dump` (a `CancellationToken` for the dump ID numbered by the frontend), which kills the child process. The command preview (`preview_command`) goes through the same argument-building function as execution, replacing only the option file and the tunnel port with readable strings. - `lib/editor/sqlCompletion.ts` — Schema completion (tables / columns / aliases, CYBERNEURA-DEV-1355). **lang-sql's `schema` option is not used** (`sql()` only does keyword completion, and this is added via `dialect.language.data.of({ autocomplete })`). lang-sql's completion (1) only offers columns after `table.` / `alias.`, (2) matches names case-sensitively (`u.` in `FROM Users u` offers nothing), (3) only sees aliases inside `SELECT ... FROM` (`UPDATE t x SET x.` offers nothing), and (4) reads SQL Server keys `[dbo].[users]` as a name hierarchy `[dbo]` → `[users]`, so plain `users` offers nothing — these were why "completion often doesn't appear". It is a pure function `completeSql(model, doc, pos, explicit)` depending on neither CodeMirror nor the syntax tree (`tests/sql-completion.test.mts`), and with its own small lexer (strings / quoted identifiers / comments / words; nested block comments only for PostgreSQL, `#` comments only for MySQL, square brackets only for SQL Server) it collects table references and aliases from `FROM` / `JOIN` / `UPDATE` / `INTO` across **the whole statement containing the cursor** (`;`-delimited; it also reads a `FROM` after the cursor) (including inside subqueries, without distinguishing them). What it offers: for an unqualified word, "columns of the referenced tables (boost 20, the source table name in detail, same names merged into one) → aliases → all tables → schemas"; right after `FROM` / `JOIN` / `UPDATE` / `INTO` / `TABLE`, tables first (no columns); `x.` resolves in the order alias → a table of that name referenced by the statement → a table with the same name → schema (its tables); `s.t.` gives columns. Inside strings, comments, the middle of a number, or an empty word (except an explicit Ctrl+Space), null. A bare name prefers the "key without a schema" (= the default schema), and otherwise all tables with that name. `s.t` is that schema's table; if `s` is a schema name not in the map, it is treated as a table in the default schema (because PostgreSQL's `public` / DuckDB's `main` are omitted from keys, and MySQL can qualify with the current database name). For names differing only in case, an exact match is preferred. Key splitting (`splitQualifiedKey`) reads square brackets only for SQL Server and just splits on `.` for the others (the backend writes names exactly as the catalog spells them). Comments count as whitespace when collecting references, and PostgreSQL dollar quoting (`$tag$ ... $tag$`) counts as a string. Names identical to reserved words (`order` etc., `RESERVED_WORDS`) are inserted quoted. The inserted string is quoted only when the dialect requires it (PostgreSQL quotes if it contains uppercase. Tables in another schema are `schema.table`; SQL Server inserts the key `[dbo].[users]` as-is = the same as insertion from the TABLES pane). Inside quotes (`"Am|"`) only the contents are replaced. **An unclosed quote swallows the SQL after it**, so if the text from the cursor to the closing quote is not a word, it cuts at the cursor and re-reads what follows as SQL. Scanning covers up to 100,000 characters before and after the cursor (`completionWindow`; a guard against files grown huge by Run and Log comments. SqlEditor does not call `doc.toString()` and passes only that range via `sliceDoc`). The model (`buildCompletionModel`) is built only once per schema map (the all-tables / schemas candidates `topLevel` are also prepared here), and columns are looked up on each completion only for the referenced tables, so the former "drop columns above 2,000 tables" cap is no longer needed. **Freshness of the schema map** (`app.svelte.ts`): (a) It keeps `schemaMapCache` (connection + active schema → map), and connection switching (`applyConnectionContext`) and `loadSchemaMap` show the cached map while waiting for the fetch (previously it was set to null on every switch, and completion was empty until the catalog query returned. Showing the cache does not open a connection. It is discarded on config reload). If the fetched result is the same, `schemaMap` is not replaced (`sameSchemaMap`; replacing it rebuilds the editor's completion). (b) A failed fetch is retried after 2 seconds and after 10 seconds (previously completion stayed absent until the next connection / schema switch). (c) If a successfully executed statement starts with `CREATE` / `ALTER` / `DROP` / `RENAME` (`changesSchema`), it calls `get_schema_map` with `refresh: true`, discarding and re-fetching the backend's SchemaCache (including the table list) (`refreshSchemaAfterStatement`; for both single statements and batches). **It does not re-fetch for a connection with no editor tab** (`maybeDisconnectIfIdle` disconnects right afterwards, so a catalog query arriving after the disconnect would reopen the tunnel with nothing to close it again). In that case, and for connections that are not selected, the frontend cache is discarded and only a mark is put in `staleSchemaConnections`, so the next `loadSchemaMap` adds `refresh`. Writing to the cache only happens when it is "the latest request for that key" and "the same generation across config reloads" (`schemaMapRequestSeq` / `schemaMapCacheEpoch`, so a late, stale response does not overwrite the post-DDL re-fetch). The backend's SchemaCache also advances an `epoch` on each invalidation and does not cache the result if an invalidation happened after the query started (`put_all_columns_if_current`). Schema changes made by other clients are not detected (use the reload button in the TABLES pane). (d) For **a connection whose first connect failed** (not in `resourcesLoaded`), neither the schema list nor the completion map was re-fetched until another file was opened — queries worked because `run_query` reconnects on its own, but completion alone did not appear. `ensureConnectionResources` is now also called when an editor tab becomes active (not called if that tab was closed while waiting) and when a statement executes successfully (only for the selected connection that has an editor tab) (a no-op if already established. Imports are merged into one per connection generation (`connectionLifecycleGen` + `connectionsResetGen`) = `resourceImports`. A trigger after an intervening disconnect does not piggyback on an import started before the disconnect (which is discarded on completion)). - AI chat pane (ChatPane) — The pane on the right, opened and closed with `data-annotate="toggle-chat-pane"` on the toolbar (width and open state are persisted in localStorage `queryfolio.layout.chatWidth` / `chatOpen`). The conversation state is held by the frontend (`chatMessages` in `app.svelte.ts`), and the whole history is sent to the `ai_chat` command on each round trip. The backend (lib.rs) builds the system prompt (dialect + schema) and runs the `run_sql` tool execution loop. **The agent's SQL always goes through the read-only guard** (fixed to `ReadonlyGuard::Agent` regardless of the Writable switch or the config's readonly, and `allow_dangerous_statements` is not passed either). `Agent` denotes both the origin and the strength, and **in addition to statement-level checks it enforces read-only at the DB level**: Postgres wraps it in `BEGIN READ ONLY`, MySQL in `START TRANSACTION READ ONLY`, DuckDB in `BEGIN TRANSACTION READ ONLY`, always followed by ROLLBACK, and SQLite sets `PRAGMA query_only = 1` (`readonly_begin_sql` / `set_sqlite_query_only` / `run_query_readonly` in db.rs). Statement-level checks alone cannot see through function calls with side effects such as `SELECT nextval(...)`, so the final rejection is left to the DB itself. If starting fails, the whole query errors out (fail-closed). Key design points: (1) Postgres / MySQL use sqlx's `begin_with` — sending a raw `BEGIN` would mean that when an abort drops the query's future, no ROLLBACK runs and a connection with an open transaction goes back to the pool. sqlx's `Transaction` also queues a ROLLBACK on drop, which avoids this. (2) SQLite's `PRAGMA query_only` is a session setting, so cleanup on drop cannot be relied on — rather than "turning it off", **run_query_on / run_statements explicitly set 0/1 on every execution**, so the next execution always overwrites any lingering setting. (3) DuckDB executes synchronously while holding the Mutex, so the ROLLBACK always completes within the same blocking closure. Remaining limits (measured; confirmed on PostgreSQL 17 / MySQL 8.4; also stated in the docs): (a) **temporary objects are outside read-only transactions on both engines**, so writes to them go through, (b) **MySQL DDL leaves the transaction via implicit commit, so it is not rejected** (what stops DDL is the statement-level whitelist. Postgres rejects DDL too), (c) writes to other systems (dblink / postgres_fdw), (d) the contents read themselves. - `\c <database>` / `USE <database>` — Switching the active schema (database). It cannot be translated to SQL, so `run_query` in `lib.rs` handles it before acquiring the pool (`switch_active_schema`). **Executing `USE` as SQL as-is does not switch**: MySQL's `USE` is a per-session change, so it has no effect on the next query that lands on another connection in the pool. In addition, `USE` is not a fetch-type statement, so the readonly guard (is_readonly_allowed) rejects it. So `meta_commands::translate` maps `USE <database>` to `MetaCommand::Connect`, the same as `\c`, and solves both by recreating the whole pool (switching is not a write, so it is allowed even with Writable OFF). Only MySQL / PostgreSQL, where `\c` is available (PostgreSQL has no `USE` statement, but it is accepted because people type it out of MySQL habit). sqlite / duckdb do not support `\c` itself, and DuckDB's `USE` works natively, so it is executed as normal SQL. The argument goes through the same identifier validation as `\c` + stripping of the dialect's quotes (`` ` `` for MySQL, `"` for PostgreSQL). A trailing semicolon and trailing comment (`USE mydb; -- switch`) are dropped via `body_end` of `scan_sql` (so the per-dialect comment rules are not rewritten. MySQL executable comments `/*! ... */` are treated as code by scan_sql, so they stay in the body and are rejected by the multi-statement and argument checks below). Multiple statements (`USE db; DELETE ...`) are rejected because the second statement would be silently discarded (a `;` remaining within `body_end` is evidence of a second statement). The agent path (`ReadonlyGuard::Agent`) does not go through `run_query`, so `run_query_on` in `db.rs` turns `MetaCommand::Connect` into an error (the agent is not allowed to change connection state). `set_schema_override` discards and recreates the pool, then runs a confirmation `SELECT current_database()` / `SELECT DATABASE()` on the switched connection and returns its result (an empty result would make success hard to see). If it cannot connect, `replace_schema_override` rolls back to the original schema (without rolling back, every subsequent query would be left unable to connect). The switch target is returned to the frontend in `QueryResult.switched_schema`, and `applySwitchedSchema` in `app.svelte.ts` updates `activeSchema` (the schema browser subscribes to changes in activeSchema so it follows automatically; the completion schema map is re-fetched). sqlite / duckdb are not supported because the schema is the DB file path

Meta-commands (`\c db` etc.) have no `;` and lezer merges them with the next line's statement into one Statement, so lines starting with `\` are cut out one line at a time as separate statements (blank lines and `--` lines in between are skipped). When the selection fits within one statement, it is the statement at the cursor as before. redis / es keep the existing path of sending the selection as-is to the backend. The result tab shows not each statement's result but **a summary per statement** (`#` / status (`ok` / `error` / `cancelled` / `running` / `not run`) / rows / elapsed_ms / statement / message), rebuilt after each statement for progressive display (ResultsPane shows the grid during running only for batch tabs). `executeTab` is not used — it empties the result and drops running per statement, so the summary could not stay on screen, and another execution on the same connection could cut in between statements. Instead **the tab stays running for the whole batch** (`isConnectionRunning` also applies between statements and during error confirmation, and `maybeDisconnectIfIdle` does not cut the tunnel). Cancellation only reaches the running statement, so it is recorded in `batchCancelRequests` and also stops before the next statement. **A selection containing transaction / session statements (BEGIN / COMMIT / ROLLBACK / SET / LOCK / temporary tables etc.; `lib/batchSession.ts`) is not executed as a batch** — run_query takes a separate connection from the pool for each statement, so the UPDATE in `BEGIN; UPDATE ...; ROLLBACK;` would be committed on a different connection (there is no mechanism to pin a session). Dangerous-statement confirmation is per statement. A batch started with Writable ON stops at that point if Writable drops midway (switching connections also drops it) — matching the existing rule that writes are only allowed on the selected connection. Continuing would make all remaining statements fail as Read-only, and pinning Writable to its value at the start would write to an unselected connection, and since `confirmIfDangerous` looks at the effective Writable and skips the confirmation, dangerous statements would run without confirmation. On failure, `BatchErrorModal` asks "Stop / Ignore errors and run all", and choosing the latter means later failures do not stop it. Prompts are pushed **as a queue** in `batchErrorPrompts` (if a batch on another connection fails at the same time, replacing would stop the earlier batch without asking, and a click meant for it would apply to the later batch. The modal shows the connection name). Cancellation and config reload close the relevant prompts with Stop. While a batch is running, switching that connection's Database is forbidden (a guard in `changeActiveSchema` + the selector disabled) — each statement runs on the connection's current schema, so switching would send the remaining statements to a different DB. Detecting the change on the batch side would be too late because the frontend's `activeSchema` is updated after the backend finishes switching. `changeActiveSchema` awaits saving and the chat abort, so it re-checks afterwards before incrementing the count in `schemaSwitchingConnections`, and `runBatch` / `rerunTab` look at it via `batchStartBlocker` and refuse to start (exclusion in both directions). Switches and reloads can overlap, so both are kept as counts rather than booleans (so the one finishing first does not remove the guard of the one still running). A config reload stops all batches **before** `resetConnections`, and during a reload (`reloadsInProgress`) new batches are not allowed to start — the reset removes the schema override, so until the tab is discarded, the next statement could be sent to the config's default DB. `ResultTab.batch` holds the list of statements; Re-run re-executes the whole list, and cell editing and Analyze with AI are not offered. - Row virtualization of the result table (ResultsPane) — **Do not put all rows × all columns in the DOM**. The row count is capped by `max_rows`, but **the column count has no cap**, so 500 rows × 61 columns makes 31,000 cells, and input in the CodeMirror editor in the same document stalls (CodeMirror forces a synchronous layout on every key press. Measured at 17ms per keystroke, and in real use to the level of **dropping keystrokes**). In addition, every cell subscribes to `selection` via `cellBgClass` / `isSelectedCell`, so every cell's effect is re-evaluated on each drag selection. The fix is a set of three, and **it does not work if any one of them is missing**: (1) Render only the visible range + an overscan of 10 rows, keeping the scroll extent with top and bottom spacer `<tr>`s. (2) Use **`border-separate` + `border-spacing: 0`** instead of `border-collapse` (each cell draws its own `border-b border-r`, so it looks the same, but WebKit's border-collapse layout path is heavy, and this alone took 17ms → 5ms). (3) `table-layout: fixed` + explicitly specified column widths (with virtualization, auto layout would decide column widths from "the cells being rendered" only, so widths would move while scrolling). Key design points: **`table-layout: fixed` only takes effect when the table's `width` is not `auto`**, so `min-w-full` (= `min-width`) does not work and it falls back to automatic layout (col widths become mere hints). But with `width: 100%`, columns get compressed below their specified widths when the pane is narrow (e.g. when the cell inspector is open). So **`width: max(100%, sum of column widths)`** is specified explicitly: when narrow it scrolls horizontally, and when wide **a filler column with no width** (`<col>` + `<th>` + a `<td>` in each row) absorbs the remainder (without the filler column, the remainder is distributed proportionally to all columns and the `#` column becomes extremely wide). Since the font is monospace, column widths can be derived directly from the character count in `ch` units (no DOM measurement needed), but **CSS `ch` is based on half-width characters, so using `String.length` as-is makes Japanese columns half as wide as needed** — `displayWidth()` counts East Asian Wide / Fullwidth as 2. **This width calculation must always be cut off at a cap (`MAX_COL_CHARS`)**: without the cap the cost is proportional to the **total character count** rather than the number of cells, and long TEXT columns cause freezes of seconds (`db.rs` does not truncate cell text on the sqlx path, so a 100KB TEXT arrives as-is. Measured 500 rows × 3 columns × 100KB: 1,971ms → 1ms with the cap). Caveats that come with virtualization: **`blur` does not fire when the focused element is removed from the DOM**, so when the cell being edited goes out of the rendered range, an `$effect` commits it explicitly (`commitCellEdit` looks up the target tab from `editingCell.tabId`, not `activeTab` — at the time of switching to another tab, `activeTab` is already the destination). When a row unmounts and focus falls to `body`, Cmd+C / Cmd+A stop working, so focus is restored, but **this is done in an `$effect` that subscribes to `rowWindow`, not in the scroll handler** (at scroll time the row is still in the DOM, and a one-off scroll like PageDown produces no further scroll event). When replacing the result, reset **both `scrollTop` and `scrollLeft`**, and subscribe to **`executedAt` too**, not just `activeTabId` (`prepareTargetTab` reuses unpinned tabs, so re-running in the same tab does not change `activeTabId`). **`rowWindow.start` must always be clamped to the last row** (right after switching to a result with fewer rows, `scrollTop` is still the old value, so `start > end` and zero rows are rendered)

Display cuts each value at 2,000 characters (`ROW_DETAIL_MAX_CHARS`), and JSON pretty-printing is applied only to values within 20,000 characters (decided after serializing only within budget with `stringifyBounded`, so that even a row with many columns of 100KB values does not clog the DOM or the main thread). Tests are `tests/row-detail.test.mts`
- Manual transactions (CYBERNEURA-DEV-1398) — **Per connection, one at a time**, for the pooled sqlx engines (capability `supports_manual_transaction` = mysql / postgres / sqlite; SQL Server and DuckDB already run everything on one connection). Backend (`db.rs`): `DbManager::begin_transaction` takes one connection out of the pool, sends BEGIN **through sqlx's `TransactionManager`** (so sqlx knows the depth: a nested `begin` becomes a SAVEPOINT, and the agent guard's `begin_with("BEGIN READ ONLY")` fails instead of opening and later rolling back a second transaction — a raw `BEGIN` would let that ROLLBACK undo the user's transaction), and keeps it in `DbManagerInner.transactions` as a `ManualTransaction` (id numbered per manager, the connection behind a tokio Mutex, the pool for the cancel target). **The connection is `close_on_drop`**: everything that drops the pool also drops the transaction (`reset` / `disconnect` / schema switch / its rollback, a discarded pool after a failed cancel), and closing makes the server roll back — it never goes back to the pool with a transaction open. `end_transaction` takes it out of the map first (new statements get `AppError::TransactionEnded`), waits for a running statement, then COMMIT / ROLLBACK; the connection is closed either way. `run_query` (`run_query_in_mode`) routes by **the backend's state**: an open transaction takes every statement of the connection (Display and FullFetch) even without the frontend's id, and a passed `transaction` id that is not the open one runs nothing (`TransactionEnded`; otherwise the statement would auto-commit while the user expects Rollback to undo it). With a transaction open, `\c` / `USE`, `set_active_schema`, the Run and Log re-fetch (agent guard) and cell edits (`run_statements`, its own transaction on another connection) are refused. **Statements that end a transaction by themselves are caught on the database, not by parsing SQL**: after every statement in a transaction, `ensure_still_in_transaction` asks the session — PostgreSQL `SAVEPOINT queryfolio_probe` (+ RELEASE; refused with 25P01 outside a transaction block, 25P02 = a failed transaction, still open), SQLite `BEGIN` (fails inside a transaction, opens one outside), MySQL `SELECT @@autocommit` (the session runs with `autocommit = 0`, set in `begin_manual`, so DDL / LOCK TABLES / a deadlock open a new transaction instead of leaving the rest auto-committed; a statement that turned autocommit on committed) — and when the transaction ended it opens a new one at once and the run reports it (`AppError::Session`; a session that does not answer is closed, and its record is pruned the next time the transactions are read = `prune_closed_transactions`, so the connection is back in Auto). The keyword checks below only catch the plain spellings for a better message. The session's cancel id (PG backend PID, read after BEGIN for PgBouncer / MySQL CONNECTION_ID) is read once in `begin_manual` (after an error PostgreSQL refuses every statement, so reading `pg_backend_pid()` per statement would also block `ROLLBACK TO SAVEPOINT`). PostgreSQL's COMMIT is preceded by `SELECT 1` (`end_manual`: COMMIT of a failed transaction is a ROLLBACK that sqlx reports as success; a refused probe becomes an explicit rollback reported as "Not committed"). A MySQL deadlock (SQLSTATE 40001) says that the whole transaction was rolled back. `end_transaction` takes the connection out of its `Mutex<Option<_>>`, so a statement that got hold of the transaction earlier finds it ended, and counts in-flight COMMIT / ROLLBACKs (`transaction_ending`) so that quitting during one waits for it. Several statements in one run are refused inside a transaction (the checks look at the first statement only). `set_schema_override` refuses while a transaction is open under the same lock as the switch. Quit / Exit in the menu is an app item (`quit_app`, CmdOrCtrl+Q) instead of the predefined one, because the predefined Quit terminates without `ExitRequested` on macOS. `session_statement_rejection` applies to the pooled engines: outside a transaction it refuses BEGIN / START TRANSACTION / COMMIT / END / ROLLBACK / ABORT / SAVEPOINT / RELEASE / LOCK / UNLOCK / RESET / session SET (MySQL `SET GLOBAL` / `PERSIST` / `PASSWORD` / `@@global.` run) with a pointer to Manual; inside one, BEGIN / COMMIT / END / ABORT / ROLLBACK (not `ROLLBACK TO`) / PREPARE TRANSACTION and a SET that mentions `autocommit` anywhere. Words are read from `scan_sql`'s cleaned text (comments and literals skipped). Quitting (`RunEvent::ExitRequested { code: None }`, the main window's `CloseRequested`) with open transactions is held by `hold_exit_for_transactions`: a native dialog, "Roll Back and Quit" → `rollback_all_transactions` (5 seconds each) → `app.exit(0)`. Frontend (`app.svelte.ts`): `transactions` (a `Map` connection → id, `$state.raw` replaced on change: connection names may be `__proto__`) mirrors the backend; every run captures the connection's transaction id when it is asked for and refuses if it changed by the time it is sent (`transactionChangedSince`; a batch sends all its statements with the id it started with); `startTransaction` is refused during a config reload; `syncTransactions` (`list_transactions`) re-reads it after every run on a transaction connection and warns when one ended underneath (a version counter drops answers older than a local begin / end). `finishTransaction` refuses while the connection is running, and `isConnectionRunning` counts a pending begin / end (no statement may slip into the gap between them and auto-commit); Commit / Rollback restart a transaction (stay Manual), switching to Auto rolls back after asking. `maybeDisconnectIfIdle` keeps a connection with a transaction; closing its last editor tab, reloading the config ask (`ask` of plugin-dialog = capability `dialog:allow-message`) after saving, roll back explicitly, and stop if the rollback was refused (a failed end is checked with `list_transactions` before the transaction is dropped from the state). DDL run inside a transaction re-reads the completion map after the commit (`schemaChangedInTransaction`; the re-read right after the statement ran on another connection that does not see it). Batches skip `sessionStatementReason` in Manual (each statement runs on the session). Tests: `test_session_statement_rejection_*`, `test_manual_transaction_sqlite` and `_postgres` / `_mysql` (with `QUERYFOLIO_TEST_PG_URL` / `QUERYFOLIO_TEST_MYSQL_URL`; PostgreSQL 16 via pgserver verified, MySQL not). Not verified on a real device: the toolbar, the dialogs, the Quit item and the window close on macOS / Windows
- Named query parameters (`lib/queryParams.ts` + `QueryParamsModal.svelte`, CYBERNEURA-DEV-1400) — `:name` placeholders are filled in **in the frontend right before running from the editor** (`fillQueryParams` in `+page.svelte`, called by `runStatement` and `runStatements` = the batch path). Values come from `-- @set name = <SQL>` comment lines of the active editor tab (`parseDefinitions`; the value is inserted as written; `definitionFor` = the last definition above the statement's SQL body (`sqlBodyOffset`: the editor range can start with comment lines, e.g. after a bare `--` line), otherwise the first in the file; a comment line so the file stays valid SQL for other tools), and the remaining names are asked for once per run in the dialog (string literal by default via `quoteParamString`, SQL Server uses `N'…'`; `raw` inserts as written). The dialog's last values are kept in localStorage `queryfolio.queryParams` per connection + file. **Text substitution, not driver binding**: sqlx binds an untyped value as TEXT, so PostgreSQL rejects `int_col = $1`. The guards (readonly / dangerous / auto LIMIT) and the history see the filled-in text because only that is sent. **`RunTarget` stays as the editor's text** — Run and Log compares the target range with `target.sql` before writing back, so the filled-in SQL is passed separately (`runQuery(sql)` / `runQueryForLog(sql, …)`). If the active tab or connection changed while the dialog was open, it does not run. Detection (`findParams` over `blankNonCode`) ignores strings, quoted identifiers, comments, PostgreSQL / DuckDB dollar quotes and `E'…'` strings, PostgreSQL and SQL Server nested block comments, MySQL `#` comments (`--` only before whitespace, as MySQL requires), SQL Server / SQLite `[…]` (`]]` escape), `::` casts, `:=`, a colon right after an identifier / number / `)` / `]` / `.`, a colon after the end of a string or quoted identifier (DuckDB `{'k':v}`; told apart from a quote inside a comment with `blankNonCode(…, keepLiterals)`) or after a bare key in a key position (right after `{` or `,`) inside DuckDB `{…}`, and a colon after a subscript `[` in PG / DuckDB, whitespace allowed (`arr[:n]`, `arr[ :n]`; `ARRAY[:id]` and DuckDB `[:id]` are constructors and keep their placeholders — a bracket written right after its operand is a subscript). `-- @set` lines count only where `--` really starts a comment (not inside a string, dollar quote or block comment; `blankNonCode(…, keepLineComments)`), and the file text is LF-normalized first (editor offsets are LF). **Literals are mode-independent**: without a backslash `'…'`; with one, MySQL `CONVERT(X'<utf8 hex>' USING utf8mb4)` (NO_BACKSLASH_ESCAPES) and PostgreSQL `E'…'` (standard_conforming_strings = off). Lookups use Maps (page, dialog, remembered values stored as `[name, value]` pairs) or own properties (`fillParams` with a record), so `:constructor` / `:__proto__` work. One dialog at a time; "Remember values" can be turned off (localStorage is plain text). The run is dropped if the tab, connection or database changed while the dialog was open (single and batch). Engines: `paramEngineOf` (redis / es / DynamoDB PartiQL are excluded). Not applied to EXPLAIN, Re-run (re-runs the filled-in text) or the TABLES pane's Show definition. Tests: `tests/query-params.test.mts`
- `lib/sqlFormat.ts` — SQL formatter (its own tokenizer. Only SELECT / UNION-type statements are formatted; INSERT / UPDATE / WITH etc. and unparseable statements are left as written. It has a safety net that re-tokenizes the formatted result and reverts to the original if the token sequence does not match the input)
- Run and Log (`lib/runLog.ts`) — When you execute a statement directly below a line comment that starts with `-- 📝 <label>`, the result is written back below that statement as a block comment (TSV) starting with `/* 🗒️ <label> <execution time>` (CYBERNEURA-DEV-447. The SQL editor version of **runandlog** (CYBERNEURA-DEV-442)). Display in the result table is unchanged; the write-back is a copy. Marker detection (`findRunLogLabel`) looks only at "the line comments immediately and contiguously preceding the execution target" and "the comments contained at the start of the execution target [from, to)" (outside the execution target, if there is a blank line or another statement in between, it is another statement's marker). Key design points: (1) **`*/` and `/*` in the written body must always be neutralized** (`escapeBlockComment`). Leaving `*/` closes the comment there, and the following data lines get executed as SQL. `/*` cannot be left either — PostgreSQL block comments **nest**, so an unclosed `/*` swallows the entire rest of the file into a comment. (2) **Re-running replaces the existing block** (same as runandlog: no matter how many times you run it, there is one block). Treating the first `*/` after `/* 🗒️` as the end is only possible because (1) removes `*/` from the body. If the existing block is unclosed, it writes nothing and reports it (adding before a broken comment only increases the nesting). (3) The insertion point is after the trailing whitespace and `;` of the statement (lang-sql's Statement includes the `;`, but when it does not, this avoids inserting before the semicolon). Blank lines before and after are normalized to one line, so writing the same result does not change the text (idempotent). (4) **Execution completes asynchronously**, so before writing back it checks three things — "the source tab still exists and has the same connection", "the active schema is still the same as at the start of execution (excluding the destination switched to by `\c` / `USE`)", and "the text in the target range matches the executed SQL" — and **the label is re-read from the text at write-back time** (the marker line alone can be edited even when the SQL does not change, and a same-length rewrite slips through the range check. If the marker itself has been removed, it is treated as a cancellation and nothing is written) (`SqlEditor.writeRunLog`; the same idea as `replaceRangeIfMatches`). If anything has shifted, it writes nothing and reports it in a toast. It does not move the cursor or focus (the user may be editing somewhere else while waiting). **It writes even if you moved to another tab during execution** (CYBERNEURA-DEV-858): `writeRunLogToInactiveTab` in `app.svelte.ts` rewrites that tab's text (`tab.content`) directly and saves it immediately with CAS (the auto-save schedule can only hold one tab, and scheduling would steal the schedule of the other tab being edited). The decision uses `planRunLogWrite`, shared with the editor path, and in addition it does not write if the tab was closed, moved to another connection, or is in conflict (`conflicted`). An unedited CRLF file is normalized to LF before checking, the same as CodeMirror (target positions are LF-based). While another connection is open, `activeSchema` is not that connection's, so the schema of the executing connection is asked for with `getActiveSchema`. If you come back to the tab during that wait, it switches to the editor path (it does not replace the displayed text wholesale). (4.5) **The log contains all rows, not the 500 rows of the result table** (CYBERNEURA-DEV-1167). The result table is cut by auto LIMIT (`default_limit`), so if the result of a 📝 statement was cut (`runLogNeedsFullFetch` = the row count reached applied_limit / truncated), `runQueryForLog` in `app.svelte.ts` runs it once more **as a continuation of the same execution** (`afterRun` of `executeTab`; the result tab stays running) and writes that result. The re-run is only for statements that `can_rerun_for_output` can determine are read-only, and the backend's `QueryMode::LogRefetch` (`log_refetch` of `run_query`) executes it with (a) no default_limit, (b) registration in QueryRuns = Cancel reaches it, (c) **`ReadonlyGuard::Agent` regardless of Writable** (the statement whitelist + READ ONLY transaction / query_only. Unlike Copy / Export, it runs without any extra user action, so the side effects of `SELECT nextval(...)` must not happen twice), and (d) rejection if the active schema differs from the one at display execution time (`expected_schema`). `\c` / `USE` do not switch in this mode. For statements that cannot be re-run or whose re-run failed, the displayed result is written with annotations as before (nothing is written if cancelled). The inline cap is `RUN_LOG_FETCH_MAX_ROWS` (20,000 rows. Rows go through the WebView, so it is about what the body cap `MAX_BODY_CHARS` warrants). **If the label has `out=<file name>`** (`parseRunLogLabel`. The first token that stands as an independent word. It is removed from the heading), all rows are written to the same connection folder as the query file, and below the statement only `(N rows written to <name>)` is written (following runandlog's `out=`). **File serialization is done by the backend** (`run_log_output.rs`. CSV / JSON / otherwise TSV by extension; conversion and the formula guard follow the same rules as export.ts): cells have no character cap, so building the strings for all rows on the WebView's main thread would freeze it. When a re-run is needed, `run_log_to_file` streams up to 1,000,000 rows with LogRefetch and writes them directly without returning rows to the frontend. When not needed, the displayed result is passed to `write_run_log_output`. The name is checked by `query_files::run_log_output_name` (path separators, leading `.`, query file extensions `QUERY_FILE_EXTENSIONS` (tests check it when engines are added), `_queryfolio.md`. It also does not replace existing directories etc. The text may be written by an agent via the CLI `write`, so it must not be allowed to write outside the folder or to query files), and this is also done before the re-run. The file is written before the block (so a block pointing at a file that could not be written is never left), so even if writing back the block is skipped because it is stale etc., the file has been written. On re-run failure, cancellation, or a schema change, the file is not written (the previous file is kept). For statements without a result set (INSERT etc.), no file is created and the affected row count is written inline. (5) **For results over 200 rows (`RUN_LOG_CONFIRM_ROWS`), a confirmation dialog (`RunLogConfirmModal`) is shown before writing back, letting the user choose "write all / write only the first 200 rows / don't write"** (CYBERNEURA-DEV-518). At exactly 200 rows, writing all is the same amount, so it does not ask (the check is `>`, not `>=`). The threshold and the row count for "write only part" are the same constant because with different values the dialog could not explain how many rows you would get. **A row cap alone is not enough** — cell text has no cap, so even a few rows can reach hundreds of MB if there are long TEXT / JSON columns. It also cuts off by total characters (`MAX_BODY_CHARS` = 1,000,000 characters; raised from 200,000 when DEV-1167 started writing all rows) and by characters per cell (`toTsvCapped`), and states in the body that it was cut. There are four kinds of notes at the end of the body, and **each is a different fact, so the wording is made distinguishable**: `(limited to N rows)` = chose to write only part in the dialog / `(the query was limited to N rows)` = auto LIMIT actually dropped rows / `(the result itself was truncated)` / `(this log was truncated …)`. **The auto LIMIT note is written only when rows were "actually suppressed", not when "a LIMIT was added"** — if `LIMIT 500` was added but only 5 rows came back, nothing was dropped, and writing it would be a false warning that "there is more" (judged by `result.rows.length >= result.applied_limit`. At exactly the cap, whether there is more is unknown, so it errs toward writing it). (6) The target is **only SQL-language editors** (redis / es have different syntax for both line and block comments). lang-sql always makes block comments sibling nodes of Statement, so a written-back block never gets mixed into the execution range of the next statement. (7) **Line comments do not necessarily become siblings of Statement**. If there is a line with only `--` and no content, lang-sql does not make it a LineComment, and **everything from that line to the SQL becomes one Statement** — explanatory comments, blank lines, and the `-- 📝 label` line all end up in the execution range together. Therefore the forward scan of `findRunLogLabel` (skipping comments at the start of the execution range to find the SQL body) **must not stop at blank lines** (CYBERNEURA-DEV-516). Instead it stops at the end of the execution range `to` — going outside the range would pick up the next statement's marker

## CLI (options that do not start the GUI)

### Installing the `queryfolio` command (macOS)

The app menu's `Install Command Line Tools…` (`cli_install.rs`) creates a symlink at `/usr/local/bin/queryfolio`
pointing to the executable inside the `.app` (the same approach as dagscape / beckwell). If `/usr/local/bin` is
not writable, it asks for the administrator password via `osascript`'s `with administrator privileges` and runs only
that one operation as administrator. An existing symlink is replaced; a file that is not a symlink is not overwritten
and results in an error. It does not link to an App Translocation path (an app opened from the download location or a
dmg with the quarantine attribute still set) — the location changes on every launch, so the link would be broken next
time. It does not exist on Windows (the Homebrew cask has no `binary` either).

- **A launch via the symlink (`current_exe()` is a symlink) does not run the GUI in that process.** Running the `.app`'s
  executable directly from a terminal makes the GUI hang off the terminal (closing it kills the app), so it finishes the
  informational options and the `write` output in the current process, then relaunches with `open -n <bundle> --args <arguments>`
  (if an instance is already running, the new process's single-instance hands over the arguments and exits). The
  traditional usage of invoking the `.app`'s executable directly (not a symlink) is unchanged.
- The relaunched process's cwd is `/`, so relative paths for `open` are made absolute using the caller's cwd.
- **`write` drops the content and relaunches with `--cli-write-done` prepended** (`WRITE_DONE_FLAG`). The relaunched
  process sees this mark and skips the write — when an instance is running, not skipping would run
  `config_override_command` (1Password etc.) again just to hand over the arguments. **When no instance is running, it runs
  twice even with the mark, once on the terminal side and once in the launched app** (there is no way to pass the merged
  config to the new process; a known limit). The reason not to switch to `open <written path>` is that a path looks the
  connection up again from the folder, so if two connections share the same folder, it could not be opened. The mark is
  only honored when it comes before the subcommand (if the `write` content happens to be the same string, it is still written).

`--help` / `--version` / `--license` / `--list-servers` / `--stats` write to stdout and end with `std::process::exit` (if `--weeks` of `--stats` is invalid, it writes to stderr and exits with 2).
They are collected in `cli.rs`, and `run()` checks them with `cli::info_command_from_args` before building Tauri
(and before the `write` output).

- **If a subcommand comes first, they are not looked at**. In `queryfolio write conn a.sql "--help"`, the third argument is
  the content to write, not an option. It scans rather than using fixed positions because macOS sometimes inserts
  arguments like `-psn_0_12345` at the front when launching a `.app`
  (the same reason as `route_from_cli_args`).
- **`--list-servers` does not output passwords, SSH keys, or passphrases.** The only fields output are
  `ConnectionInfo` (a projection without sensitive data that is passed to the frontend) and the folder name; `ServerConfig`
  is read directly only for the TLS decision. Keep to this path when adding fields (guaranteed by tests).
- The TLS column **outputs the effective mode as-is** for mysql / postgres / redis
  (`disable` / `prefer` / `require` / `verify-ca` / `verify-full`). The default `prefer` means
  "try TLS, downgrade to plaintext if it cannot be established, and do not verify the certificate", so rounding it to yes/no
  would hide unencrypted connections. Engines without an effective mode output `tls` as `on` / `off`.
  **Do not fall back to `tls` just because `ConnectionInfo::sql_ssl_mode` is `None`** —
  `None` covers not only "engines with no concept of an effective mode" but also the case where "the `engine` / `ssl_mode` value
  was invalid and could not be resolved", and outputting `on` / `off` for the latter would **present a
  config that errors at connect time as a valid TLS setting** (a typo like `ssl_mode: requre` would read as `off` = connects in
  plaintext). When it cannot be decided, it outputs `invalid` (`ssl_summary`).
  **However, `invalid` is output only for "engines where that value actually makes the connection fail"** —
  only the mysql / postgres branches of `db::connect` read `ssl_mode`, and the
  elasticsearch / sqlite / duckdb / dynamodb paths do not look at it. Even if an invalid `ssl_mode` slips in via a shared
  template etc., those connect normally, so outputting `invalid` would make usable connections look broken.
  The meaning of `invalid` is "this config will not connect", not
  "the config contains an invalid value".
  **A config whose `ssl_mode` resolves but is rejected in combination is `invalid`** — specifying `ssl_root_cert`
  together with a mode that does not verify it (`disable` / `prefer` / `require`, including the default `prefer`
  when `ssl_mode` is omitted) makes `sql_ssl_root_cert` return an error, so `db::connect` always fails.
  Outputting `prefer` from the effective mode alone would make a connection that cannot connect look valid.
  However, **it does not check whether the root CA actually exists as a file (`is_file` of `ssl_root_cert_path`)**
  — building the display is pinned down by unit tests as a pure function that does not touch the file system,
  and a missing file that can be put in place later is not the same as a config error.
  **Even for engines where `tls` does not determine the actual connection method, do not output it as-is** —
  dynamodb's `host` / `port` / `tls` are solely an endpoint override for dynamodb-local,
  and a normal AWS connection without `host` has the SDK resolve the regional endpoint, always over https
  (`build_client` only builds `endpoint_url` when `host` is present). Outputting the default
  `tls: false` would **make an encrypted connection read as plaintext**, so without an override it outputs
  `on` (`has_endpoint_override`). When adding an engine, first confirm "whether `tls` determines that engine's
  actual connection method".
  **But "no `host` = regional endpoint" does not hold either.** `aws_config::defaults` also
  reads endpoint override settings, so if `AWS_ENDPOINT_URL=http://localhost:8000` is in
  effect, it connects in plaintext. Environment variables are resolved by `cli::aws_endpoint_override` in the same
  order of precedence as the SDK (`AWS_IGNORE_CONFIGURED_ENDPOINT_URLS` → `AWS_ENDPOINT_URL_DYNAMODB` →
  `AWS_ENDPOINT_URL`), and `on` / `off` is derived from the URL's scheme. The resolution is done in
  `run_info_command` in `lib.rs` and passed to `format_server_list` (building the table is kept as a pure function
  that does not depend on the process environment either). **The `endpoint_url` /
  `services` sections of `~/.aws/config` are not looked at** — we want to keep a path that does not read files, and copying the SDK's
  profile resolution would create a second implementation that drifts from the real one. In environments that override
  via a profile, it shows `on` (a known limit).
- **`--list-servers` shows dynamodb's USER as `(hidden)`.** This `user` is an AWS
  access key ID, not a DB username (`folder_meta.rs` replaces it with
  `(aws access key, hidden)` for the same reason, and `sqlfiles_folder_name` hashes it), and it is
  not a value to leave in the terminal and shell history (`user_cell`). It is a different word from `-` for unset —
  "no static key configured" and "configured but not shown" are different facts.
  **`ConnectionInfo` is a projection that is "OK to pass to the frontend", not one that is "OK to print to the terminal".**
  Some fields like `user` change meaning by engine, so when adding a column, do not pass it through as-is.
- **The Windows release build has no console.** Because of
  `windows_subsystem = "windows"` in `main.rs` it is linked with the GUI subsystem, so
  `GetStdHandle(STD_OUTPUT_HANDLE)` returns an invalid handle and `print!` is silently discarded.
  This would make the informational options, whose purpose is display, useless, so before displaying,
  `cli::attach_parent_console` (`AttachConsole(ATTACH_PARENT_PROCESS)`) reattaches to the parent process's
  console. **Not verified on real Windows** (neither the development host nor CI has Windows,
  so only type checking for the Windows target has been done).
- **The above only fixes the output destination; it does not fix "the shell not waiting for exit".** When a GUI
  subsystem exe is launched from cmd.exe / PowerShell, the shell returns to the prompt without waiting for it to exit.
  So in an interactive shell (1) output may appear after the next prompt, and
  (2) `%ERRORLEVEL%` / `$LASTEXITCODE` do not become the exit code of the informational option.
  Redirection and pipes work as usual (the handles are inherited, and the reader waits until the writer
  closes), so use from scripts is unaffected.
  **Fixing this would require adding a separate console-subsystem exe to the distribution, with the side effect of a
  console window appearing on GUI launch and a change to the distribution that cannot be verified in this environment.**
  The app's main purpose is the GUI, so that trade has not been made. If you need the exit code in an interactive shell,
  use `Start-Process -Wait queryfolio -ArgumentList '--list-servers'`.
- Building the display (`help_text` / `format_server_list`) is kept as pure functions that depend on neither Tauri nor the
  file system, pinned down with unit tests. Loading the config and output are in `run_info_command` of `lib.rs`.
  `--list-servers` writes to stderr and exits with 1 if loading the config fails.
- **The version number is `version` in `tauri.conf.json`, not `CARGO_PKG_VERSION`.** Releases are
  determined by that version (`release.yml`), while the version in `src-tauri/Cargo.toml` does not
  follow it, so outputting `CARGO_PKG_VERSION` would make `--version` answer 0.1.0 even when the
  distribution is 0.1.4. `build.rs` reads `tauri.conf.json` and embeds it as `QUERYFOLIO_VERSION`
  (failing the build if it cannot be read), and `APP_VERSION` in `cli.rs` uses it.
  `test_version_comes_from_the_tauri_config` prevents the drift from recurring.
- From the macOS `.app`, `open -a Queryfolio --args --list-servers` does not return stdout.
  Use the installed `queryfolio`, or invoke the binary directly as `Queryfolio.app/Contents/MacOS/queryfolio --list-servers`.

## `queryfolio://` scheme / CLI (opening files)

Saved query files can be opened by path via the URL scheme or the CLI. Both go through the
common router in `router.rs`, so adding an action in the future only requires adding a `Route` variant and
its parsing to support both.

- **URL scheme**: `queryfolio://open/<absolute path>` (e.g. `queryfolio://open//Users/me/.config/queryfolio/sqlfiles/reporting/monthly.sql`. It is an absolute path, so `/` is doubled after the scheme). macOS receives the URL natively (`queryfolio` in `tauri.conf.json > plugins > deep-link > desktop > schemes` is registered in Info.plist at bundle time). On Linux/Windows, the `single-instance` plugin (deep-link feature) forwards the URL from a second launch to the running instance.
- **CLI**: launch the app binary with the `queryfolio open <path>` subcommand. If an instance is running, single-instance brings that window to the front and opens it there; otherwise it opens after a fresh launch (from the macOS `.app`, `open -a Queryfolio --args open <path>`, or `open "queryfolio://open/<path>"` takes the same path).
- **CLI (write and open)**: `queryfolio write <connection name> <file name> [content]`. It is specified by **connection name + file name** rather than a path, so the caller does not need to know `sqlfiles_dir` or the folder naming rules (aimed at AI agents). The content is passed as the third argument or via **stdin**. The connection engine's extension is added, and the connection folder is created if missing (`_queryfolio.md` is also written). Key design points:
  - **The write is performed by the launched process itself before Tauri starts** (`apply_cli_write_route` in `lib.rs`). single-instance forwards only argv and cwd to the running instance and **does not forward stdin**, so leaving the write to the running instance would lose content passed through a pipe. The forwarded `Route` is used only as an "open" instruction, and the `WriteFile` branch of `resolve_route_target` **does not write** (even if the content arrives twice via argv, it is not written twice).
  - **On failure it does not continue launching and exits non-zero** (`run` calls `std::process::exit(1)`). Continuing and only "opening" would open the old contents even though the write failed, which would look like success to the calling agent. stdin has a 10MiB cap, and exceeding it is an error without truncation (writing partway would break the query).
  - **Empty stdin is treated as "no content specified"** (an existing file is not clobbered). With a GUI launch (`open -a Queryfolio --args write ...`), stdin is /dev/null and hits EOF immediately, so interpreting it as "write empty" would silently erase the existing query file. If stdin is a terminal it is not read either (it would hang waiting for input). When no content is specified, it only does "create it empty if missing" (`query_files::ensure_query_file`).
  - **`write` is not accepted from a URI** (`parse_uri` makes it UnknownAction). `queryfolio://` can be opened even from a Web page, so allowing writes via URI would let the page being viewed plant arbitrary SQL as a query file (with the danger that a human runs it later). Unlike `open`, which only reads, writing is CLI-only.
  - If the running instance already has that connection selected, `selectConnection` is a no-op and a file created externally does not appear in the FILES list. `openFileByTarget` re-fetches `listQueryFiles` if the file name is not in the list.
- **Security**: only query files (`.sql` / `.redis` / `.es`) in connection folders directly under the query file storage directory (`sqlfiles_dir`) can be opened. `resolve_open_target` squashes `..` traversal by lexical normalization and rejects paths outside the storage area, unknown folders, disallowed extensions, and names starting with a dot (pure validation that does not touch the file system). Whether the extension matches the connection engine's is additionally validated by lib.rs (resolve_route_target).
- **Wiring**: a target given at launch is recorded by setup in `AppState.launch_route`. Right after registering its listener in onMount, the frontend calls the `frontend_ready` command once and receives and opens, all at once, the launch target + those that arrived and were queued during startup (before the listener was ready). Later targets while running are resolved by Rust and delivered directly via the `open-query-file` (success) / `open-query-file-error` (failure) events, and `openFileByTarget` in `app.svelte.ts` selects the connection and opens the file (drops before the listener is ready are prevented by the ready flag in `AppState.live` + a queue).

## Config (config.yml)

Configuration is consolidated in `~/.config/queryfolio/config.yml` (or `config.yaml` if that does not exist). There is no settings.json.

- `servers` is a list of server definitions (each entry is written directly in the sql-agent-mcp-server-compatible format; the equivalent key there is `sql_servers`). Writing a mapping is an error. The old names `sql_servers` / `sql_server_templates` are not kept for compatibility; at parse time (reject_renamed_keys in config.rs) they become an error that points to the rename (silently ignoring them would make the cause of having zero connections impossible to find). Old names inside nested group entries are also rejected by parse_server_entries.
- Groups (a queryfolio extension) — Writing `group_name:` + a nested `servers:` list as an item of the `servers` list shows the servers inside it with a group heading in the connection list (ConnectionsPane). At parse time it is flattened and recorded in each `ServerConfig.group_name` → sent to the frontend as `ConnectionInfo.group_name` (parse_server_entries in config.rs). Mixing with directly written servers is allowed, and they are shown in config order. Nested groups (depth 2 or more) and keys other than group_name / servers / color in a group entry are errors. `template:` inheritance works inside groups too.
- Connection color `color` (a queryfolio extension, CYBERNEURA-DEV-1207) — The `color` of a server (and of a group entry) is passed to the frontend as `ConnectionInfo.color` and shown as a 3px left edge on the CONNECTIONS row (`ConnectionsPane`), the background of the connection name in the toolbar (25% via `color-mix`; while Writable is ON, a border of the same color via `box-shadow`), and a dot before the connection name in editor tabs / result tabs (`appStore.connectionColorOf`). A server's own color takes precedence over the group's color. **The value is fed into CSS, so it is limited to a closed grammar**: `normalize_color` in `color.rs` only lets through CSS color names (148 colors + transparent, case-insensitive) and `#rrggbb` / `#rgb`; anything else makes `parse_server_entries` (`validated_color`) print a warning to stderr and leave it uncolored (the whole config does not fail, so a typo in a decorative key does not make a connection disappear. Non-strings such as lists and numbers are also routed through the same "invalid color" path by `deserialize_lenient_color` / `color_value_to_raw`, rather than becoming a serde error). When a server's own color is invalid, it does not fall back to the group's color (uncolored). `rgb()` / `hsl()` / hex with alpha are not allowed.
- `config_override_command` (optional, a queryfolio extension) — Runs the given command and **recursively merges** its stdout (YAML) into the whole config (the fetched YAML takes precedence). Any key can be overridden, not just `servers`, so while keeping API keys and connection info in 1Password etc., you can also replace `default_limit` and `sqlfiles_dir`. The merge rules are `merge_mapping` in config.rs: **mappings are merged recursively, while scalars and sequences (including servers) are replaced wholesale** (lists are not merged element by element because element identity cannot be determined). Even if the fetched YAML contains `config_override_command`, it is not fetched recursively, and the key is dropped after merging. Resolution is `AppConfig::load_merged` (async). `AppConfig::load` is a synchronous version that reads only the local file, used for things like deciding which menu items to show (has_config_override_command). **The merged config is cached once per session in AppState** (the fetch command takes several seconds + Touch ID with 1Password etc., so it is not run on every query execution). default_limit / sqlfiles_dir / the connection list / ai are all derived from this cache, so there are no separate caches (to avoid forgetting to clear one). Cleared by reset_connections. If the key exists but is not a string, or is an empty string, it is an error (silently treating it as "unset" would hide the fact that the override is not taking effect and it is running on the local config). Configs using the old style (declaring a source under the old key `sql_servers`) become an error, and the message guides migration to `config_override_command` (reject_renamed_keys outputs it together with the rename guidance). Note that `View override config yaml (Copy only)` does not go through the cache and runs the command every time (intentionally, since its purpose is checking and copying the current value in the storage).
- `config_override_command` is run without a shell (split with shlex). To handle the minimal PATH of a GUI launch, /opt/homebrew/bin and /usr/local/bin are supplemented. 60-second timeout + kill_on_drop.
- `password_command` (optional, a queryfolio extension; external PR #128 / CYBERNEURA-DEV-994) — Per connection, specifies a command that fetches the password (time-limited credentials such as RDS IAM auth tokens). The password is stdout with only trailing `\r` / `\n` removed (tokens contain `&` `=` `%`, and some passwords contain spaces, so nothing else is touched). Empty output, non-UTF-8, and a non-zero exit are errors. **It runs only when `DbManager::get_pool` creates a new pool (once even if it reconnects in a loop), on every dump (dump.rs; dumps do not use the pool and connect on their own), and when expiry is detected** — not when loading the config, selecting the connection, or for other connections. The result is put into the `ServerConfig.password` duplicated by get_pool and passed to `connect()`, so every engine that reads password works without engine-side changes. Validation (`ServerConfig::password_command`) happens at connect time, like ssl_root_cert: specifying it together with password (including from a template; use `password: null` to cancel it out), sqlite / duckdb, and an empty string are errors. **Expiry (Postgres / MySQL only)**: an sqlx pool uses the password from its creation for connections it opens later too, so a pool with a token that expires in 15 minutes starts failing on new connections even while existing connections are alive. Commands that use the DB go through `DbManager::with_pool` (or `run_with_password_refresh` if the pool has already been acquired), and on an authentication error they re-fetch password_command, replace only the password with `Pool::set_connect_options`, and retry the operation **just once**. Which authentication errors are retried is declared by the caller with `PasswordRetry`: **`BeforeStatement` (user SQL = run_query / run_statements / AI tool execution) only retries `AppError::ConnectAuth`** — `DbConnection::acquire` (the first step of each function) relabels connect-time authentication failures as this variant (displayed the same as Db). A 28P01 raised by a statement stays `AppError::Db` and is not retried (the PR's first version re-ran the whole operation based only on the final error's code, and a nextval before PL/pgSQL's `RAISE ... USING ERRCODE = '28P01'` ran twice; reproduced on a real PG). **`Idempotent` (catalog queries = TABLES / columns / PK / schema list / completion map, and cancellation) retries any authentication error** (the implicit acquire cannot relabel it as ConnectAuth, but they run no user code and running twice is harmless). Key design points: (1) **Re-fetching is single-flight per pool** — under the `connecting` connection lock, it compares against the `RefreshState` recorded before the operation (an Arc of the pool's current connect options + the count of failed re-fetches on that pool, `password_refresh_failures`); if unchanged, it runs the command; if changed, someone else has re-fetched for that pool (on success the Arc is replaced) or tried and failed, so it only retries. Failures are counted too so that each waiting operation does not re-run a failing helper (which would line up prompts or 60-second timeouts as many times as there are operations). **It is per pool rather than per connection name** because some operations still hold an old pool discarded by a schema switch or reload, and re-fetching for that one would not change the current pool's password (pointed out by Codex). The Arc is held for the comparison (if freed, the replacement could reuse the same address and the comparison would lie). An implementation that "counts at start" made an operation that failed during execution run the helper once more (detected by a test). (2) **It cannot be detected by an acquire probe**: a returned connection is pinged by a spawned task before going back to the pool (sqlx-core 0.8.6 `pool/connection.rs`), so the acquire right after a probe often opens a new connection, and even if the probe passes, the operation fails with the expired password (this approach was implemented once and rejected in review). (3) The pool is not recreated (so it also takes effect on copies held by CancelTarget, and authenticated connections and the tunnel are kept). (4) **Cancellation also opens its own connection**, so `cancel_query` / `cancel_ai_chat` go through `cancel_with_password_refresh` (otherwise a query running longer than the token's lifetime could no longer be stopped). What gets re-fetched is not the cached pool but **the pool held by that query's CancelTarget** (`CancelRegistry::registration`; it can differ after a schema switch), and the retry is **limited to the same registration ID** (`cancel_registration`, because while waiting for the helper's prompt the original query may finish and the next query may register under the same key). (5) The confirmation query of `\c` runs on a pool recreated on the spot, so it is not wrapped. When adding a command that uses the DB, go through `with_pool` and choose `PasswordRetry` correctly (calling `get_pool` directly does not recover from expiry). mssql / redis / elasticsearch / dynamodb are not covered by the automatic re-fetch (same password until the pool is discarded; mssql's MsSqlHandle uses the Config from creation time for reconnects after cancellation and on the agent path). **Trust boundary**: a password_command written in the YAML of `config_override_command` is also executed, so anyone who can edit that source can run commands on this machine (a warning is written in the docs). **Confidentiality**: the output is never exposed to the frontend (`ConnectionInfo` only has `password_from_command: bool`; the hover shows `Password: (command)`), logs, history, errors, or AI. `View override config yaml` runs only config_override_command. Verification against real DBs is `test_password_command_against_postgres` / `_mysql` (run only when `QUERYFOLIO_TEST_PG_URL` / `QUERYFOLIO_TEST_MYSQL_URL` are given).
- `default_limit` (optional, default 500, 0 disables) — Automatically appends `LIMIT n` to SELECTs without a LIMIT (should_auto_limit in db.rs; conservatively skips subquery LIMITs / FOR UPDATE etc.).
- `readonly: true` (optional, default false; a queryfolio extension to the sql-agent-compatible format) — Rejects execution of write statements (INSERT / UPDATE / DELETE / DDL etc.) on that connection. The decision is is_readonly_allowed in db.rs: if leading_keyword is anything other than select / with / show / describe / desc / explain / pragma / values / table / call it is rejected, and in addition it rejects, using word-boundary checks after removing literals and comments, WITH with CTE DML (insert / update / delete / merge), SELECT INTO for SELECT, EXPLAIN ANALYZE + DML for EXPLAIN (because it actually executes the target statement), and the assignment form of PRAGMA (SQLite DB changes containing `=`, such as `PRAGMA journal_mode = WAL`). Meta-commands are read-only, so they are always allowed. It cannot prevent functions with side effects in SELECT (nextval etc.) or setting PRAGMAs in parenthesized form; it is only a guard against accidents.
- `allow_dangerous_statements: true` (optional, default false; a queryfolio extension) — When omitted, dangerous statements (UPDATE / DELETE without WHERE, DROP, TRUNCATE) are rejected to prevent destroying all rows or losing tables by mistake (dangerous_reason in db.rs: word-boundary checks via scan_sql, the same as readonly. UPDATE/DELETE check for the presence of the word where; DROP/TRUNCATE are always dangerous). Not only the leading keyword, but also dangerous DML inside wrapper forms that actually write — `WITH ... DELETE/UPDATE` (Postgres CTE DML) and `EXPLAIN ANALYZE ...` (executes the target statement) — is covered. Setting it to true allows execution, but the frontend shows a confirmation dialog (DangerousConfirmModal) before running. Whether confirmation is needed is decided by the check_dangerous_statement command (dangerous_statement_reason in db.rs). readonly is evaluated first, so on readonly connections this guard is never reached. Weakness: in WITH, if an unrelated CTE / the outer SELECT has a where, a DML without WHERE is missed (the typical form containing no where at all is caught). A where only inside a subquery likewise errs on the permissive side.
- `sqlfiles_dir` (optional) changes the query file storage location. The default is `~/.config/queryfolio/sqlfiles/<folder>/<name>.sql`. **A relative path is resolved against the config directory (`~/.config/queryfolio`), not the current directory** (`resolve_sqlfiles_dir` in config.rs). The CLI `write` is written by the launched process itself, while opening is done by the running instance (a separate process with a different cwd), so with cwd as the base the written location and the opened location would differ. The cwd of a GUI launched from Finder (`/`) is also meaningless as a base. `<folder>` uses the per-connection `folder_name` setting if present, otherwise `<host>_<engine>_<schema>_<user>` is built (the connection name is not used; `ServerConfig::sqlfiles_folder_name` in config.rs; path separators etc. are sanitized). Note that if the folder name of an existing connection changes, the previous query files stay in the old folder. Each folder gets an automatically generated metadata file `_queryfolio.md` describing the connection (folder_meta.rs; non-sensitive only, and since it is not `.sql` it does not appear in the UI lists).
- `folder_name` (optional, a queryfolio extension) — Explicitly sets the query file storage folder name. For the folder name rule when omitted, see `sqlfiles_dir` above.
- `ssh_tunnel.identity_agent` (optional, a queryfolio extension) — Explicitly specifies the agent socket used for ssh-agent auth (equivalent to OpenSSH's IdentityAgent). `none` disables the agent. When omitted, it is resolved in the order IdentityAgent in `~/.ssh/config` → SSH_AUTH_SOCK (tunnel.rs). A solution for environments that keep keys in the 1Password SSH agent and launch from the GUI.
- `ssh_tunnel.ssh_config` (optional, a queryfolio extension) — Writing a Host alias name from `~/.ssh/config` delegates that connection's tunnel to the system `ssh` client instead of libssh2 (`ssh -N -L`). **Multi-hop tunnels via ProxyJump** and resolution of HostName / User / Port can be handed entirely to OpenSSH and `~/.ssh/config` (e.g. writing `ssh_config: pop-three-ec2-staging` makes that Host's `ProxyJump pop-three-bastion` etc. take effect as-is). In this mode host / user / password / private_key_* / identity_agent in the same `ssh_tunnel` are ignored, and both authentication and host key verification are left to OpenSSH (`BatchMode=yes`, so on unknown host keys or passphrase prompts it errors out without interaction. Agent auth works because it is handled on the agent side). The traditional libssh2 path when ssh_config is omitted remains as-is (host is required).
- `ai:` (optional) — Settings for AI SQL generation (`provider: openai` / `api_key` / `model` optional / `base_url` optional / `tool_reasoning_effort` optional). `tool_reasoning_effort` is the `reasoning_effort` attached only to AI chat (function calling) requests. Reasoning models such as gpt-6-luna / gpt-6-sol / gpt-5.6-luna / gpt-5.6-terra return 400 when tools are used with `/v1/chat/completions` unless `reasoning_effort` is `none` (`To use function tools, use /v1/responses or set reasoning_effort to 'none'`), so **`none` is sent by default only when the endpoint is official OpenAI (base_url omitted or the official URL)**. When `base_url` points at an OpenAI-compatible API, it is sent only when explicitly specified (so as not to arbitrarily break a chat that used to work with a counterpart that does not accept this parameter). Specifying an empty string means it is never sent. It is not attached to SQL generation / EXPLAIN explanation requests, which pass no tools, so their reasoning quality is unaffected. **Which values pass differs by model** (gpt-4o-family models do not accept this parameter at all), so no list of model names is kept; when a 400 is caused by `reasoning_effort`, **it removes the parameter and resends just once** (`rejects_reasoning_effort` / `remove_reasoning_effort`). It works with new models without adding settings. However, for models that do not accept `none` (gpt-6-astra), removing it and resending gets a different 400, "tools and reasoning_effort (the default when omitted) cannot be combined", and the AI chat cannot be used (there is no way to rescue it with Chat Completions; supporting it would require migrating to the Responses API). **The abort is also checked right before this resend** (the `is_cancelled` argument of `chat_step` / `request_chat_completion`. The caller `run_ai_chat` only checks for aborts before and after `chat_step`, so if Stop / Clear / a schema switch happens while waiting for the first response, only the second request would slip through. If discarded, it stops with `AppError::Cancelled`). The SQL generation / EXPLAIN explanation paths, which have no abort, pass `never_cancelled`. It can be written both at the top level of the local config.yml and at the top level of the YAML fetched by `config_override_command`. **If both exist, the fetched YAML takes precedence** (as a result of the merge, so the API key can be kept in 1Password). `ai` is a mapping and so is merged recursively; writing only `api_key` on the fetched side keeps the local `model` etc. Currently the only provider is openai, and unknown values are errors. Cached per session in AppState and cleared by reset_connections.
- `agent:` (optional, CYBERNEURA-DEV-1354) — The coding agent used by the chat pane and the AI field above the editor (`provider: claude | codex` / `directory` optional / `directories` optional = connection name → directory / `auto_accept_edits` optional, default true). Without `provider`, it stays the built-in assistant (`ai:`). An unknown provider is an error. Unlike `ai:`, it has no cache and is parsed from the merged config every time (`AppState::resolve_agent_config`). Directories are absolute paths (`~` allowed), and existence is checked when the agent starts. It can also be provided by `config_override_command`. Details in agent.rs and docs/agent-chat.md.
- The `QUERYFOLIO_CONFIG_YAML` environment variable is a development / test hook that overrides the entire config file (used for end-to-end verification on a real machine).

See `config.example.yaml`. mssql (alias sqlserver, a queryfolio extension) treats `schema` as the database name (master if omitted) and connects with SQL Server authentication via user / password. It is an SQL engine, so meta-commands / `\c` / EXPLAIN (the SHOWPLAN pseudo-statement) / auto LIMIT (TOP) / Format / AI / TABLES / SSH tunnels are available; only cell editing is not supported. `ssl_mode` / `tls` / `ssl_root_cert` are the same as mysql / postgres (verify-ca is equivalent to verify-full). sqlite is an extension that treats `schema` as the DB file path. duckdb (a queryfolio extension) likewise treats `schema` (or `host` if absent) as the DB file path, but if the file does not exist it is an error (it is not created). It is an SQL engine, so meta-commands / EXPLAIN / auto LIMIT / Format / AI / TABLES work as with other SQL engines; only cell editing and `\c` (because the schema is a file path) are not supported. redis (alias valkey, a queryfolio extension) treats `schema` as the database number, and the editor is 1 line = 1 command. **The DB number can be switched with the Database: field above the editor** (CYBERNEURA-DEV-408. The choices are built from `CONFIG GET databases`, defaulting to 16 if that cannot be fetched. Switching takes effect via schema override + pool recreation, the same as SQL engines). While Writable is OFF only the whitelist of read commands is allowed, and FLUSHALL / FLUSHDB / SHUTDOWN / DEBUG require `allow_dangerous_statements`. Query files use the `.redis` extension, and TABLES / Explain / Format / cell editing / AI are not supported (hidden from the UI entirely via capabilities). elasticsearch (aliases es / opensearch, a queryfolio extension) connects with host/port (default 9200) + user/password (Basic auth) + `tls: true` (https, a queryfolio extension), and the editor uses Kibana Console-style request blocks. While Writable is OFF only GET/HEAD + a whitelist of search POSTs are allowed, and index deletion (`DELETE /<index>`) and `_delete_by_query` require `allow_dangerous_statements`. Query files use the `.es` extension; TABLES (indices + mapping fields) is supported, while schema switching / Explain / Format / cell editing / AI are not. dynamodb (a queryfolio extension) is an SQL-editor engine that runs PartiQL via the ExecuteStatement API: `schema` = AWS region (required), `host`/`port` = endpoint override for dynamodb-local etc. (`tls: true` for https, port defaults to 8000 if omitted), and auth is user/password (static access key) → `aws_profile` (a queryfolio extension, a profile name in ~/.aws) → the default credentials chain, in that order. PartiQL has no LIMIT clause, so auto LIMIT is not applied, and the row count is bounded by the API's limit + max_rows. Query files use the `.sql` extension; TABLES (tables + key schema / attribute definitions) and Format are supported, while meta-commands / schema switching / Explain / cell editing / AI / SSH tunnels are not. **`tables` (trailing semicolon allowed) is a queryfolio-specific statement that returns the table list**; PartiQL has no SHOW TABLES, so it bypasses ExecuteStatement and goes to ListTables. It is a pure read, so it is handled before the readonly / dangerous guards and can be executed even with Writable OFF (CYBERNEURA-DEV-406). While Writable is OFF only SELECT is allowed, and UPDATE / DELETE without WHERE require `allow_dangerous_statements`.

## Development notes

- **The app name is written "Queryfolio" everywhere users can see it** (window title / toolbar / productName / comments in the generated config file / README headings etc.).
  **The `f` is lowercase**; `QueryFolio` is wrong (fixed across the board in CYBERNEURA-DEV-805. Do not "revert" to camel case).
  The repository name, bundle identifier (com.cyberneura.queryfolio), and crate name remain all-lowercase queryfolio.
  `productName` determines the macOS `.app` name, the app menu, and the dmg / installer file names.
  **If you change it, update the Homebrew cask to match (`url` / `app` / `name` in `Casks/queryfolio.rb` of
  cyberneura/homebrew-tap). The order is "publish the artifacts with the new name first, then fix the cask"**
  — fixing the cask first makes it point at artifacts that do not exist yet, and `brew install` returns 404
  (the tap's auto-update leaves a cask whose artifact download failed as it is, so until publication
  it keeps working at the old version).
  Note that **the executable binary name inside the bundle is the crate name, not `productName`** (lowercase
  `queryfolio`). tauri uses cargo's output as-is unless `mainBinaryName` is specified.

- **Comments written on PRs (PR descriptions, replies to reviews, PR comments) are also written in English**.
- **`skills/queryfolio/SKILL.md` duplicates facts about the implementation, so when you change the relevant parts, fix it too** (it is distributed with `npx skills add cyberneura/queryfolio`, and agents read it and act on it). In particular: the Run and Log constants (`RUN_LOG_CONFIRM_ROWS` / `MAX_BODY_CHARS` / `MAX_CELL_CHARS` / the wording of the notes), query file permissions and ordering, how the `--list-servers` columns are decided, the stdin handling of `resolve_write_content`, and the behavior of the external change watcher. **Prose is not executed, so CI does not fail when it goes stale** — in fact, the old version this skill was based on had drifted from the implementation in 5 places (the confirmation dialog threshold 500 → 200, the permissions of `sqlfiles/`, making `config.yml` 600, the 3-way merge of external changes, the list order).
- Put `data-annotate="<identifier>"` on elements that receive user actions (for E2E tests).
- Do not use `window.prompt` / `alert` / `confirm` (they block browser automation + UX).
- 64-bit integers get rounded at the Tauri invoke boundary when they exceed JS's Number.MAX_SAFE_INTEGER, so json_i64 / json_u64 in db.rs turn out-of-range values into strings.
- **Always write character ranges in regular expressions with `\u` escapes** (not as character literals). Characters that look the same can be different code points: in the full-width check in `ResultsPane.svelte`, `豈-﫿` was written intending U+F900-FAFF (CJK Compatibility Ideographs), but the "豈" in the source was actually **U+8C48**, making the range U+8C48-U+FAFF, which **swallowed the surrogate area (U+D800-DFFF)**. As a result, `.test()` without the `u` flag happened to judge every supplementary-plane character as width 2 (emoji looking correct was a coincidence; Mathematical Alphanumerics U+1D400 were wrong). When handling the supplementary planes, also use the `u` flag + code-point iteration with `for...of`.
- **When adding frontend processing that scans every cell of a result, always cut it off at a cap**. `db.rs` does not truncate cell text on the sqlx path, so a 100KB TEXT or a long JSON string reaches the frontend as-is. An implementation whose cost is proportional to "total characters" rather than "number of cells" brings second-long synchronous blocking into a path that row virtualization was supposed to make light (measured: 500 rows × 3 columns × 100KB took 1,971ms).
- sqlx is strict about Postgres numeric type compatibility (INT4 can only be decoded as i32, etc.). When adding a decode, check the `compatible` implementations in the sqlx sources under ~/.cargo/registry.
- sqlite `:memory:` is a separate DB per pool connection. Use max_connections(1) in tests.
- macOS signing has `APPLE_SIGNING_IDENTITY` (Developer ID Application: Cyberneura K.K.) set in the `tauri` script in package.json. `pnpm tauri build` (local) is signed with this (not notarized). `bundle.macOS.signingIdentity: "-"` in tauri.conf.json is the ad-hoc signing fallback when the env is absent (tauri-cli's precedence is env > config). CI (`release.yml`) signs with the Developer ID from the env and passes `APPLE_ID` / `APPLE_PASSWORD` / `APPLE_TEAM_ID` to go through notarization + staple.
- For verification on a real machine, create a test SQLite DB, inject it with the `QUERYFOLIO_CONFIG_YAML` environment variable, and start `pnpm tauri dev`; this does not pollute the user's real config. When operating it with orca computer-use, use paste-text rather than type-text for text input (type-text sometimes delivers twice). **If the installed Queryfolio is running, the dev build exits right after starting** (it has the same bundle identifier, so single-instance hands argv to the existing instance and exits. The user may be using it with production connections, so do not operate that window). Ask them to quit it first.
